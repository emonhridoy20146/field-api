## [Unreleased] — contract 1.9.0
### Added
- Phase 0 implementation: core (config, errors bn/en problem+json, Dhaka time, money, geo, Mongo + migrations, event bus, outbox, Mongo-leased jobs, idempotency, change feed), module loader with manifest validation, auth (EdDSA JWT, refresh rotation with reuse detection, lockout), users, rbac (catalog, overrides, explain), branches, settings (holidays, shifts), flags (locked microfinance flag), audit (hash chain), devices (binding/approval), system (health, app-config), erp-gateway (Laravel client, circuit breaker, mappers, MockErpClient, delta sync, reconcile, posting outbox handler).
- Phase 1 modules: customers (read model + FOS overlay, status derivation, bad suggestion, list/detail/map/timeline, refresh, pin corrections), tags (tag/untag, history, approval mode, balance-cleared review), assignments (areas, primary assignee, bulk, history), handovers (receiver acceptance, 72 h expiry, temporary cover revert), collections (idempotent record, receipt blocks, anomaly flags, ERP posting with timeout-after-store recovery, conflicts, void, resolve, ERP reversal reflection).
- cash module: on-hand per staff (cash only, FIFO oldest undeposited), 80 %/100 % limit states and `cash.limit_reached` event, deposits with idempotency and verify/reject, end-of-day closing; handover summary shows the sender's cash (FR-HO-005).
- Settings `location.trackingProvider` (`free` | `paid`, default `free`) and `location.providerConfig` so the background-location plugin can be switched from admin settings later.
- Contract 1.1.0 (additive): `TagEvent.kind/deviceLocation/approvalOf`, `TagReviewItem`, `GET /customers?includeTotal`.
- Contract 1.2.0 (additive, answering staff-app gaps): `geo` may be `null` with `geoUnavailableReason` on collection/visit/attendance (flag `no_location`); `CustomerListItem.installmentPoisha/overduePoisha/areaName`; documented per-entity shapes for `SyncChange.data` and `SyncMutation.payload`; `contact_attempt` entity + `/customers/{id}/contact-attempts` (FR-M-014, server implementation pending).
- media (presigned PUT/GET 5 min, sha256 dedupe, branch-scoped reads; S3 or in-memory storage in dev/test), visits (idempotent check-in, distance to pin, flags, checkout), notes (15-minute edit window) with contact attempts, promises (date range, supersede, 09:00 reminder event, keep on ERP payment, nightly verdict with grace days, follow the customer on handover).
- Contract 1.3.0 (additive, answering admin-web gaps): `GET /rbac/overrides/branch/{branchId}` and `GET /rbac/overrides/user/{userId}`; `GET /feature-flags/effective?branchId=`; response schemas for `GET /collections/conflicts`, `GET /cash/deposits`, `GET /notifications`; `Deposit.userName`; `PATCH /notes/{id}`.
- attendance: work-in/out and break events (idempotent by `clientId`, anomalies flagged not rejected), derived day with late/break/duty minutes, absent/holiday/weekly-off/leave days, manager day grid and monthly summary, audited corrections that keep the original event, auto work-out 3 h after shift end, nightly finalize, leave requests with approval; setting `attendance.selfieRequired`; `isOnDuty()` for the location module.
- Contract 1.4.0 (additive, answering admin-web gaps): declared 200 schemas for `GET /visits`, `GET /promises`, `GET /location-proposals` (plain array), `GET /attendance/summary`, `GET /leave-requests`, `GET /broadcasts`; list rows of visits and promises carry `customer {id,name,code}` and `user`/`owner {id,name}`; location proposals carry `proposer {id,name}`; `GET /visits` gains `from`, `to`, `outcome`; `GET /promises` gains `from`, `to` and documents `customerId`.
- sync module: `GET /sync/pull` (per-user change feed, deduped, fresh data, tombstones when an entity leaves scope, `410 CURSOR_EXPIRED` beyond the 30-day window), `POST /sync/push` (ordered batch, per-item `applied | replayed | conflict | rejected`, idempotent by `mutationId`, flag + permission checked per item), `GET /sync/bootstrap` (paged snapshot ending in `pullCursor`), `GET /system/sync-health`. Modules plug in through `syncEntities` / new `syncMutations` in their manifests (ADR-027).
- Contract 1.5.0 (additive): `SyncBootstrapResponse`; `SyncPushRequest.pendingCount`; push result `retryable`, `receiptNo`, `eventId`; documented payloads for `visit_checkout`, `promise_cancel`, `cash_closing`, `handover_decision`; `DeviceSyncState.userName`; heartbeat body and `LatestLocation` gain `trackingProvider` and `trackingProviderFallback` (location module itself is Phase 2).
- notifications module: stored notification center with read state (90-day TTL), push through a `PushSender` port (log sender by default; FCM credentials are not part of this repo), quiet hours 21:00–08:00 Dhaka except critical types, `POST /devices/push-token`, event-driven notifications (promise due, handover, collection conflict/resolved, deposit decision, cash limit, tag review, pin decision, leave, auto work-out), broadcasts with acknowledgement.
- inbox module: "needs attention" items raised and auto-resolved by domain events (conflicts, posting failures, flagged collections, over-limit cash, deposits unverified > 24 h, unaccepted handovers, tag reviews, pin proposals, broken promises, absences, leave requests); resolve (audited) and snooze.
- reports module: `GET /dashboard/overview` (collected by method, visits, promises, attendance, cash, exceptions, overdue summary, ERP status, 7-day trend). search module: `GET /search` across customers, staff and receipts with per-type permission checks.
- Contract 1.5.0 also declares `Notification`, the `POST /broadcasts` response and `Broadcast.acked`.
- Tooling: ESLint config (no `any` outside one documented type, no system clock in domain code), dependency-cruiser module-boundary rules, `check:permissions`, `openapi:lint`, `check:changelog`, `db:migrate`, `seed:dev`, `new:module` with `templates/module`, HTTP mock ERP (`mock-erp/server.ts`) with a client contract test, `smoke` run of the real entrypoints, `.env.example`, Dockerfile, docker-compose, GitHub Actions CI.

- location module (Phase 2 server side): `POST /location/points` (batch ≤ 500; each point checked against the attendance duty windows — points before work-in, after work-out or during a break are refused per point with `OFF_DUTY` and never stored; also `LOW_ACCURACY`, `IMPOSSIBLE_SPEED`, `FUTURE_TIME`, `DUPLICATE`; answers `nextSampling`), `POST /location/heartbeat`, `GET /location/latest` (on-duty staff in scope, freshness, on break, mock, provider), `GET /location/history` (simplified polyline, gaps, stops matched to the nearest customer pin, summary), `GET /location/stops`; mock GPS and "tracking stopped" inbox items; nightly stops + daily summary kept beyond raw-point retention; raw points in a time-series collection whose TTL follows `location.retentionDays`. - reports (Phase 3): `GET /reports/staff-performance` (daily/monthly per field staff: visits, customers visited, collections by method, promises due/kept and fulfilment rate, attendance, field time, distance), `GET /reports/branch-trends` (collections and visits per day/week/month; overdue aging from nightly `overdue_snapshots`, today live), `GET /reports/reconciliation` (FOS collections vs. ERP field payments of a day, with mismatch kinds and `erpFetchedAt`), `POST /reports/exports` + `GET /reports/exports/{id}` (async CSV/XLSX for staff performance, collections, attendance, overdue customers, cash positions; kept 7 days; 5-minute signed link for the requester only; audited as `report.export.requested`). ADR-028.
- Contract 1.6.0 (additive): response schemas `BranchTrends` and `ReconciliationReport`; documented export `params` per type.
- `ObjectStorage.put` for server-generated files. New public functions for reports: collections `collectedByUser`/`collectionRows`, visits `visitsByUser`, promises `promiseStatsByOwner`, attendance `attendanceDays`, location `fieldStatsByUser`, customers `overdueAging`/`overdueRows`/`erpFieldPayments`, cash `cashPositions`.
- Contract 1.7.0 (additive, answering a staff-app gap): staff can follow their own pin proposals. `/sync/pull` emits entity `location_proposal` (`OwnLocationProposal`: `id`, `clientId`, `customerId`, `status`, `lat`, `lng`, `accuracyM`, `note`, `decisionReason`, `createdAt`, `decidedAt`) to the proposer only, when the proposal is created and when a manager decides; `GET /location-proposals/mine` lists them (for a reinstalled app).
- Live map and route history filled in (no schema change): `LatestLocation.todayVisits` / `todayCollectedPoisha`, the `events` overlay of `GET /location/history` (visits and collections of the day as `TimelineItem`s), and `Stop.visitId` when a visit to the stop's customer was recorded during the stop (5 minutes either side). Visit data needs `visit.view` and collection data `collection.view`; without them those parts are left out.
- Export type `audit` (CSV/XLSX, ≤ 31 days, needs `audit.view` as well as `report.export`); before/after snapshots, IPs and device ids are not exported. Contract 1.7.1 documents it (description only).
- Attendance photos (owner decision 2026-11-16, OD-12): a front-camera photo is expected at work-in, break start, break end and work-out. New setting `attendance.selfieEvents` (array of event types, default all four, per branch, sent to the app); `attendance.selfieRequired` is now the master switch and defaults to **true**. An event without a photo is still stored and flagged `no_selfie` (attendance is never lost); a `selfieMediaId` that the user did not upload is ignored. Contract 1.8.0 (additive): `GET /attendance/events?userId=&date=` (`AttendanceEvent`) so managers can see each event's photo, place and flags.
- cowork module (FR-CW-001..005, owner request 2026-11-16, ADR-029): field staff of one branch ask each other to work together for the day (`POST /cowork/requests`, idempotent by `clientId`), accept or reject (`POST /cowork/sessions/{id}/respond`), leave (`POST /cowork/sessions/{id}/leave`; work-out and auto work-out leave automatically). A person is an accepted member of one open session at a time; a session ends at Dhaka midnight (job `cowork.end-day`) or when fewer than two accepted members remain and nobody is still invited. Notifications `cowork.requested` / `cowork.responded`; sync entity `cowork_session` to every invited or member user; `GET /cowork/sessions/mine`. Managers: `GET /cowork/sessions` and `GET /cowork/sessions/{id}` with `visitsCount`. Permissions `cowork.use`, `cowork.view`; settings `cowork.maxMembers` (5, sent to the app) and `cowork.visitCredit` (1); flag `module.cowork`.
- Co-work visits: `POST /visits` and the `visit` sync mutation accept `coWorkSessionId`. The server stores `coWork { sessionId, participantIds }` with the members accepted at `checkInAt` (so a visit that syncs hours later is still right), shows the visit to the partners (list, detail, pull) and flags an unconfirmed claim `cowork_invalid` while keeping the visit. `GET /visits` gains `coWork=true|false` and `coWorkSessionId`; `userId` now also matches joint visits the person took part in; list rows carry `coWork.participants` names.
- Staff performance (and its export) gains `soloVisits`, `coWorkVisits` and `visitCredit` (= single + co-work × `cowork.visitCredit`). Every participant is credited for a joint visit; one stop recorded by two members counts once. Collections and cash are never shared: they count only for the person who recorded them.
- Contract 1.9.0 (additive): the six `/cowork/*` operations, `CoworkSession`, `CoworkMember`, `VisitCoWork`, `VisitCreate.coWorkSessionId`, `Visit.coWork`, `GET /visits` filters, `SyncChange.entity` value `cowork_session`, `StaffPerformanceRow.soloVisits/coWorkVisits/visitCredit`.
### Fixed
- `GET /location-proposals` now returns the plain array the contract has declared since 1.4.0 (it was wrapped in `{ items }`); a conformance test covers it.
### Notes
- Exports: `format: pdf` answers `422 BUSINESS_RULE` (`export_format_unavailable`) — see OD-26. `targetPoisha` stays 0 until daily targets (FR-COL-015) are approved.
- Reconciliation reads the ERP side from the cached recent payments, so "missing in ERP" straight after posting can simply mean the cache is older than the posting; the response carries `erpFetchedAt`.
- `POST /location/points` reports off-duty points per item inside the 200 response (as `docs/openapi.yaml` declares); the batch itself is not answered with `422 OFF_DUTY`, so one late point does not make the app resend 499 good ones.
- Person names in responses stay plain strings (changing them to I18nText would break v1); clients show the string as given.
- The permission catalog in `02-requirements §3.1` is the source of truth; the "50 keys" figure in the original spec text was a miscount.
- A plan ended yesterday with 1 poisha left is suggested as bad (FR-TAG-001 has no tolerance) — see OD-25.
