### Changed — contract 1.50.0 (owner request 2026-11-26: returned invoices must not be shown; FR-CUS-023, ADR-068)
- **Mapper:** an ERP invoice with status `returned` keeps plan `status: closed` (enum meanings unchanged) and now carries `returned: true`, so FOS can tell a return from a paid-off or not-collectable invoice. Nothing is written to the ERP.
- **Stored apart:** `customers.upsertFromErp` puts returned plans in `erp_customers.returnedPlans` and the rest in `plans`; `derived` is computed from `plans` only. So every client read leaves them out: customer list (`invoiceCount`, `openInvoices`, `invoiceTotals`, `invoiceKind` filter), customer detail `plans`, invoice-number search (`q`, #46) and global search, counts/KPIs built on plans, and the sync `customer` item (bootstrap and pull). The customer stays, also when all of their invoices were returned.
- **Added `CustomerDetail.returnedPlanIds`** (also on the sync `customer` item): erpPlanIds of returned invoices, so a phone that stored one before 1.50.0 deletes it. Descriptions of `Plan.status` and `SyncChange.data` updated.
- ERP payments of a returned invoice are unchanged (OD-38, default: keep).
### Migrations
- `customers/20261126-0001-set-aside-returned-plans` (forward-only, idempotent): moves returned plans cached before 1.50.0 (flag or stored `invoiceStatus`) out of `plans`, re-derives, bumps `version` and writes a change-feed entry per customer so phones get the update on their next `/sync/pull`.

- admin-web: nothing required; returned invoices simply no longer arrive. `returnedPlanIds` may be ignored.

### Fixed — contract 1.49.0 (owner report 2026-11-26: live location not shown when the staff app is closed; FR-LOC-013, ADR-067)
- **Cause:** the staff app's native foreground service keeps posting `/location/points` after the app is closed, with the access token the Dart side stored. Access tokens live 15 minutes and nothing refreshes them while the app is closed, so uploads were 401 after ~15 minutes, points stayed on the phone and the admin map froze. The native side must not refresh (refresh rotation + reuse detection would log the user out).
- **Added `POST /location/tracking-token`** → `200 { token, expiresAt }`: staff app session with a device id (else 403 `FORBIDDEN` `details.reason: APP_ONLY`) and `attendance.record` (else 403). Opaque `trk_…` token, sha256 stored (`tracking_tokens`), bound to user + device + session, valid `location.trackingTokenTtlHours` (new setting, default **24**, 1–168). Each call rotates: the previous token of the device stops working at once. Audited `auth.tracking_token_issued`.
- **`POST /location/points` also accepts `Authorization: Tracking <token>`** (security scheme `trackingToken`). The token must be live, its session live on the same device, the user active and the device approved; else 401 `UNAUTHENTICATED` with `details.reason` `TRACKING_TOKEN_INVALID` or `TRACKING_TOKEN_EXPIRED`. Permission, feature flag, body `deviceId` match and the duty-hours rule are unchanged (off-duty points are still refused per point). Rate limit unchanged and per user.
- **Every other route refuses a tracking token**: 401 `UNAUTHENTICATED` `details.reason: TRACKING_TOKEN_NOT_ALLOWED` (route-level opt-in `trackingAuth` in `core/http/router`, resolved in the core auth hook; the guard checks again).
- Tracking tokens are revoked (and audited `auth.tracking_token_revoked` with the reason) on logout (all of the user's), password change (other sessions), admin password reset, deactivation, device unbind or replacement, and when a session is ended; refresh-token reuse ends them through their session.
- 401 and 403 now documented on `POST /location/points`.
### Migrations
- `auth/20261126-0001-tracking-tokens` (indexes only, idempotent).
### Tests
- `test/integration/tracking-token.test.ts`: issue (hash only, audit, TTL), 401/403/APP_ONLY, points accepted with a tracking token 16 minutes later while the access token is refused, off-duty still rejected, body device mismatch 400, refused on other routes, unknown / malformed / sent-as-Bearer, rotation, expiry, permission denied 403, per-user rate limit, revoked by logout, password reset, device unbind and deactivation.
### Notes for the clients

### Fixed — contract 1.47.0 (owner report 2026-11-24: staff see "account blocked" at login; FR-AUTH-005, FR-AUTH-007, ADR-064)
- **Cause 1, shared IP:** `POST /auth/login` locked both the account and the client IP after 5 failures in 15 min. Staff in one office, or on one mobile carrier NAT, share an IP, so 5 wrong passwords from anyone locked everyone behind it for 15 min. If `TRUST_PROXY` was not set on Vercel, every request even looked like it came from Vercel's proxy, so the whole company shared one IP.
- **Fix:** the account lock stays at 5 / 15 min. The IP lock now needs `auth.ipLockFailures` failures (new setting, default **50**; 0 = off) and does not stop a user who logs in from a device (`X-Device-Id`) or browser (admin-web's refresh cookie) that already had a session of theirs. Anyone else behind a locked IP gets 423, right password or not, so the IP lock still stops guessing across many accounts. `TRUST_PROXY` now defaults to **true on Vercel** (`VERCEL` is set; Vercel overwrites `X-Forwarded-For` with the client IP) and false elsewhere; an explicit value still wins.
- **423 `ACCOUNT_LOCKED`** now carries `details.retryAfterSec` and `details.scope` (`account` | `ip`) besides `details.until`, and a `Retry-After` header.
- **Cause 2, device approval:** a new device for a field staff with an active device is 403 `DEVICE_NOT_APPROVED` (FR-AUTH-007). This is unchanged and is never automatic. Now the body has `details.pendingDeviceId` (the id an admin approves; the app can show it next to `requestId`), `details.deviceId`, `details.status: pending_approval` and `details.maxActiveDevices`. Retrying the login keeps the same pending device and no longer sends the managers another `device.approval_requested`.
- `POST /devices/{id}/approve`: approving an already active device answers 200 and changes nothing (was 409); the state change is atomic, so two managers approving at once bind it once. The approved device still replaces the least recently seen active device(s) to stay within `devices.maxPerUser` (the old phone is unbound and its sessions end); the audit entry lists the replaced device ids and a `device.unbound` event is emitted for each.
### Added — contract 1.47.0

True only for a pending device with the same model and Android version as the user's only active device when that device was not seen for `devices.reinstallHintIdleDays` days (new setting, default **0 = off**, so always false until the owner sets it). It is a hint for the admin screen ("same phone model, probably a reinstall"); an admin still approves.

### Fixed (owner report 2026-11-24: Atlas hit its connection limit and the database stopped answering; ADR-063)
- **Cause:** no pool options were set, so every process, that is every Vercel function instance, could open up to 100 Mongo connections (the driver default) and never closed idle ones. In busy hours, many instances together reached the Atlas limit (500 on M0).
- **Fix:** `connectMongo` now uses `mongoOptions()`: `maxPoolSize` 10 (`MONGODB_MAX_POOL_SIZE`, 1–100), `minPoolSize` 0, `maxIdleTimeMS` 60 000 (`MONGODB_MAX_IDLE_MS`), and a 15 s wait for a free connection. The API, worker, CLI and serverless adapter all use it. No contract change.
- Test: `src/core/__tests__/mongo-pool.test.ts`.

## [1.46.0] — contract 1.46.0 (customer pages of up to 1000, page jumps)

- `GET /customers`: `limit` up to **1000** (was 200; default still 50) and an optional **`offset`** (0-based, 0–1,000,000; when sent, `cursor` is ignored) that works with every filter and sort, so any page is one call. ### Migrations
- `customers/20261123-0001-customers-list-sort-indexes`: one index per list sort (`-daysOverdue`, `name`, `-totalOutstanding`, `nextDueDate`, each ending with `_id`), with and without a `branchId` prefix. Indexes only, idempotent; no data migration.

## [1.45.0] — contract 1.45.0 (sync with nobody logged in, photos upload, dashboard, follow-ups, possible customers)
### Fixed (owner report 2026-11-23: staff app photos stay "upload pending"; FR-MED-006)
- **Root cause:** `POST /media/upload-url` refused every photo from the staff app with 400 `VALIDATION_FAILED` (`capturedAt: Invalid datetime`), so the PUT and the confirm never happened and the app retried with back-off forever. The app sends `capturedAt` as `m.capturedAt.toIso8601String()` on a row of its local database (drift); drift returns DateTimes in local time, so the value has no `Z` and no offset (`2026-11-23T16:12:05.000`), and the route's `z.string().datetime({ offset: true })` only accepted `Z` or `±hh:mm`. Everything after it was fine: checked end to end in `test/integration/media-phone-upload.test.ts` with the phone's exact requests behind Vercel's proxy headers. The signed link is `https://howlader-apps-api.vercel.app/api/v1/storage/o?t=…` (from `X-Forwarded-Host`/`-Proto`, never `PUBLIC_BASE_URL`/localhost); `vercel.json` sends `/api/v1/storage/o` to `api/index.js` with the raw body (live: a forged link answers 403 `STORAGE_URL_INVALID`, so the route is reached); the app's photos are ≤ 250 KB (limits: 1 MB presign, 2 MB route, 4.5 MB Vercel); `image/jpeg` has a raw-body parser; type, size and sha256 of the app's bytes match the grant; the PUT goes without a token and the empty-body confirm works since 1.44.0.
- **Fix:** a `capturedAt` without `Z`/offset is accepted and read as Asia/Dhaka wall-clock time (+06:00); Dart microseconds are accepted. Anything that is not a date-time is still a 400. Photos already queued on phones upload on the app's next retry, no app update needed (the app should still send `.toUtc().toIso8601String()`).
### Added (owner request 2026-11-23: ERP sync without anyone logged in; FR-ERP-009, ADR-058)
- `erp.delta-sync` runs every **2 minutes** (was 5).
- `.github/workflows/cron.yml`: every 5 minutes (and by hand, `workflow_dispatch`) calls `https://howlader-apps-api.vercel.app/api/cron` with `Authorization: Bearer $CRON_SECRET` from the repository secret `CRON_SECRET`; without the secret it only prints a notice.
- Jobs catch up: a job is due when the latest slot of its schedule within its catch-up window has not run yet (default 6 h; delta sync 10 min, exports 5 min, the 09:00 promise reminders 3 h, the 23:50 overdue snapshot 9 min). Before, a job ran only when a call landed on its exact minute, so calls every few minutes skipped most slots and nearly all daily jobs. Each slot still runs once across overlapping calls (lease key = the slot's minute; an older slot never runs after a newer one).
- A cron call stays under 60 s: 40 s budget; every job gets the time left minus 8 s kept for the outbox as `budgetMs` (the delta sync stops there and continues next call), no job starts with less than 2 s left (it runs on the next call), heavy jobs (nightly reconcile) run last. `?job=<name>` passes a budget too. Tests: `src/core/__tests__/cron-slots.test.ts`, `test/integration/cron.test.ts`.
- README "Automatic ERP sync": the owner steps (below).
