# Changelog — field-api

All notable changes. Format: Keep a Changelog; contract version = `docs/openapi.yaml` `info.version`.

## [1.22.0] — contract 1.22.0 (live map shows staff on duty even indoors)
### Fixed
- **Live map stayed empty after work-in** (owner report 2026-11-19, ADR-041). The database showed the work-in saved (accuracy 200 m) but no location point: the phone indoors reports 100–500 m, and both the app and the server dropped every point worse than `location.maxAccuracyM` (50 m). The map lists only staff with a point today, so nobody showed.
- Points worse than `location.maxAccuracyM` are now **kept, flagged `lowAccuracy`**, up to 5 km (`HARD_MAX_ACCURACY_M`; beyond that still `LOW_ACCURACY`). They move the live marker but are left out of the route, stops and distance. A rough point replaces a good marker only when no good point is newer than 5 minutes. Of two points at the same instant the more accurate one is kept.
- `GET /location/latest` shows every staff member on duty: before the first tracked point of the day the marker is the position of their last attendance event (work-in).
### Added
- `LatestLocation.source` (`track` | `attendance`) and `LatestLocation.lowAccuracy`.
- `attendance` public function `lastEventGeo(userIds, date)`; field `lowAccuracy` on `location_points` and `location_latest`.
- Tests: rough points kept and flagged, never the speed reference, never on the route; work-in position on the map before the first point; a good point is not replaced by a rough one right after.

## [1.21.0] — contract 1.21.0 (attendance never waits for its photo)
### Fixed
- **Attendance still showed "1 waiting" after staff-app 0.12.0** (owner report 2026-11-19, Vercel test deployment, ADR-040). The app held the work-in until its photo was on the server, so any failed upload (old server without the `db` driver, a wrong `PUBLIC_BASE_URL`, a slow network) kept the work-in off the server, and every location point after it was refused as off duty. The owner's rule: location must go every few minutes whether the photo uploads or not.
- Storage links (`uploadUrl`, `/media/{id}/url`, export downloads) are built from the host the caller reached the API on (`X-Forwarded-Host` / `Host`, `X-Forwarded-Proto`), falling back to `PUBLIC_BASE_URL` only when the host header is missing or malformed (`src/core/http/origin.ts`). A `PUBLIC_BASE_URL` copied from `.env.example` (localhost) can no longer break uploads.
### Added
- Sync mutation `attendance_selfie` `{ eventClientId, selfieMediaId }` (permission `attendance.record`): links a photo to an attendance event that was sent without one, and removes its `no_selfie` flag. Only the person's own event and own uploaded photo; an event that already has a photo keeps it; replay-safe. The app sends it after the event (`dependsOn`).
- `GET /system/health` returns `storage` (`s3` | `db` | `memory`) so a deployment can be checked from a browser (`memory` on Vercel means uploads cannot work).
- Tests in `test/integration/storage-db.test.ts`: links follow the forwarded host and ignore a malformed one; health reports the driver; a work-in pushed without a photo is applied at once and location points after it are kept; the photo linked later clears `no_selfie`; a second photo, another person's photo or event, and a bad id are refused or ignored.
- Additive only: no route, field or meaning changed for existing clients (the old app still holds the work-in for its photo and still works).

## [1.20.1] — contract 1.20.1 (phones from before branch-wide visibility reload once; health shows the contract)
### Fixed
- Staff phones that took their snapshot while the server still showed staff only their assigned customers kept seeing only those after the server moved to 1.19.0: a feed entry goes out only when a customer changes, so the rest of the branch never arrived. The customers module now raises a **resync floor** (`counters` `sync_floor:customers-branch-wide`) at its first boot on a database with history; `GET /sync/pull` answers `410 CURSOR_EXPIRED` once for any cursor below it, and the app takes a fresh snapshot (it keeps its outbox, so a waiting attendance or collection is not lost). No reinstall, no admin step. A fresh database gets floor 0 (ADR-038 addendum).
### Added
- `GET /system/health` returns `contract` (this build's contract version, `src/core/http/contract.ts`), so the owner can see in a browser which build is deployed. The health test fails when it differs from `docs/openapi.yaml`.

## [1.20.0] — contract 1.20.0 (admin tasks for staff)
### Added
- **tasks module** (FR-TASK-001..005, owner request 2026-11-18, ADR-037): an admin or manager gives one field staff member a task with a title, a free-form note and an optional due date; it is not tied to a customer. `POST /tasks` (idempotent by `clientId`; `422 TASK_INVALID_ASSIGNEE`, `TASK_DUE_IN_PAST`), `GET /tasks` (filters `status`, `assigneeId`, `branchId`, `overdue`, `q`; `counts` per status and overdue), `GET /tasks/{id}` (with history), `PATCH /tasks/{id}` (while open), `POST /tasks/{id}/verify`, `POST /tasks/{id}/reject` (reason of at least 5 characters, `422 REASON_REQUIRED`), `POST /tasks/{id}/cancel`.
- Staff side: `GET /tasks/mine`, `POST /tasks/{id}/resolve-request` (note, optional `requestedAt`), sync entity `task` (to the assignee only; bootstrap snapshot holds open tasks and those closed in the last 30 days) and sync mutation `task_resolve_request` `{ taskId, note?, requestedAt? }`. A resolve request moves the task to `resolve_requested`; only an admin verify makes it `resolved`; a reject sends it back to `open` with the reason.
- Notifications `task.assigned`, `task.resolve_requested` (managers with `task.manage` in the task's branch), `task.decided` (verified / rejected / cancelled, to the assignee). Inbox item `task.resolve_requested` until the request is decided. Audited as `task.created`, `task.edited`, `task.resolve_requested`, `task.verified`, `task.rejected`, `task.cancelled`.
- Permissions `task.view`, `task.manage`, `task.work`; flag `module.tasks` (off by default; super admin turns it on); collection `staff_tasks` (migration `tasks/20261118-0001-tasks-indexes`).
- Additive only: no existing route, field or collection changed.
## [1.19.0] — contract 1.19.0 (staff see the whole branch, staff in several branches)
### Added
- **Field staff see every customer of their branches** (owner request 2026-11-18, FR-CUS-015, ADR-038), assigned or not, so they can visit and collect from any of them. Assignment still says whose work a customer is (`assignedTo=me`, Today, targets, handovers). New setting `customers.staffVisibility` = `branch` (default) | `assigned` (the rule before 1.19.0), per branch and sent to the app.
- **Staff in several branches:** `User.branchIds` documented as one or more for every role; the first is the home branch (attendance, cash, targets, app settings). Adding or removing a branch re-sends that branch's customers to the user's devices (they load the ones now in scope and drop the rest).
- `branch { id, code, name }` on `CustomerListItem` / `CustomerDetail`, so a list spanning several branches says which one each customer is in.
- Change feed: `sync_changes.fanoutBranchId` delivers a customer change to every device of the branch (each device's scope still applies); `/sync/pull` reads own and branch-wide entries. Index migration `sync/20261118-0001-sync-fanout-index`. Switching the setting re-sends the branch's customers the same way.
### Changed
- Reassigning a customer no longer sends a hard delete to the old assignee: the entry is an upsert and the loader turns it into a tombstone only when the customer left that device's scope (still the case under `assigned`).
- `customers.scopeFilter` is async (reads the setting); reports await it. A customer moved to another branch is dropped from the old branch's devices.
- Tests that check the assigned-only rule run with `customers.staffVisibility = assigned`; `test/integration/staff-visibility.test.ts` covers the branch-wide rule, multi-branch users and switching the setting.

## [1.18.0] — contract 1.18.0 (photos without S3: attendance and live map on the Vercel test)
Numbered 1.18.0 / ADR-039 because 1.15.0–1.17.0 are taken by PRs #18 (staff in several branches), #17 (tasks) and #16 (pin delete, ERP sync, merged as 1.17.0 with ADR-036); #17 and #18 still use ADR-036 and need new ADR numbers when they merge.
### Fixed
- **Attendance stayed "sync pending" and staff never showed on the admin live map** (owner report 2026-11-18, Vercel test deployment). Root cause: the deployment has no S3, so storage fell back to the in-memory store, which hands out `memory://` upload URLs. The phone cannot PUT to that, so the work-in photo never uploaded; the app holds an attendance event until its photo is on the server (staff-app 0.4.0), so the work-in never arrived; with no work-in the server treats every location point as off duty (FR-LOC-001, `OFF_DUTY`) and `GET /location/latest` lists only staff on duty. Visits and map pins synced because they do not wait for a photo. New storage driver `db` (ADR-039, `src/core/storage/db-storage.ts`): files go to the `storage_objects` collection behind signed URLs with the same rules as S3 (PUT and GET expire after 5 minutes; a PUT must match the signed content type, size and sha256; HMAC key derived from the JWT key, so every instance accepts the others' URLs). Exports work across function instances the same way.
### Added
- `PUT|GET /storage/o?t=<signed grant>` (public; the signature is the permission), only registered when the driver is `db`. Clients never build it: they follow `uploadUrl` from `/media/upload-url` and `url` from `/media/{id}/url` as before. Exempt from the app version gate (an old app must still finish its uploads).
- Env `STORAGE_DRIVER` (`s3` | `db` | `memory`, empty = automatic: S3 when `S3_ENDPOINT` or `S3_ACCESS_KEY_ID` is set, `db` on Vercel, S3 in production, memory in development). `PUBLIC_BASE_URL` falls back to `https://$VERCEL_PROJECT_PRODUCTION_URL` on Vercel (the signed URLs need the public host).
- Test `test/integration/storage-db.test.ts`: driver choice, upload → confirm → signed read, forged / wrong-method / expired URLs and a body that differs from the signed one, and a work-in with its photo followed by kept location points and the staff member on the live map.
## [1.17.0] — contract 1.17.0 (delete a pin, "Sync from ERP")
### Added
- **Delete a pin** (FR-CUS-014, owner request 2026-11-18, ADR-036). `DELETE /customers/{id}/location` (`customer.location.approve`): a manager deletes any in-scope customer's pin, from the ERP, the field or the map. The customer shows as "no location", the assignee's phone and polygon areas are updated, and the ERP sync keeps the pin deleted until a new pin is set. Audited `customer.location.cleared`; idempotent (`removed: false` when there was no pin).
- **"Sync from ERP"** (FR-ERP-007, owner request 2026-11-18, ADR-036). `POST /system/erp-sync` with the new permission `erp.sync` (super admin and branch manager): pulls the customers changed in the ERP now. One run at a time (lock in `erp_sync_state`), at most ~40 s per call; `partial: true` = call again. `429 RATE_LIMITED` (`SYNC_RUNNING`), `503 ERP_UNAVAILABLE`.
### Changed
- `deltaSync({ budgetMs })` keeps the page it stopped at (`erp_sync_state.resume`), always does at least one page per run, and the scheduled job honours the same `resume`.
### Checked
- New integration tests: pin delete (ERP pin, idempotent, audit, sync feed, stays deleted after `reconcile` and `deltaSync`, 403/404/401), manual sync (200, lock 429, ERP down 503, permission 403, budget + resume).

## [1.14.0] — contract 1.14.0 (map pin colours, invoice viewer)
### Added
- **Pin colour by payment state** (owner request 2026-11-18, FR-CUS-012, ADR-035): `PayState` = `bad` (red: tagged bad/legal, or a plan's full term is over with money left), `missed_many` (orange: two or more missed installments), `missed_one` (yellow: one missed), `due_today` (blue), `on_track` (green: everything due so far is paid), `paid_off` (grey: nothing left). A missed installment is a past-due line with money left, or a line the ERP rolled forward while the line that took its balance is still unpaid. `payState` + `missedCount` on `CustomerListItem`, `CustomerDetail` and `MapPin`; clusters gain `worstPayState` and `payStates` (count per colour). `GET /customers` and `GET /customers/map` take `payState=a,b` (OR) and `invoiceKind=installment|credit` (customers with an open invoice of that kind). `openInvoices { installment, credit }` on list items.
- **Invoice viewer fields** (FR-CUS-013), all optional: `Plan.payState/missedCount/daysOverdue/nextDueDate/nextDuePoisha/branchId/financedPoisha/subtotalPoisha/discountPoisha/taxPoisha/settlementDiscountPoisha/refundedPoisha/invoiceStatus/paymentStatus/creditDueDate/penalty`; items `unitPricePoisha/discountPoisha/serviceChargePoisha/lineTotalPoisha`; schedule lines `outstandingPoisha/paidOn/daysLate/missed/writtenOffPoisha/payments[]` (which ERP payment paid the line, when and how much).
- ERP field API fields read by the mapper (howlader-ERP, additive, no migration): invoice `subtotal`, `tax_total`, `settlement_discount`, `refunded`; item `unit_price`, `discount_amount`, `service_charge`, `tax_amount`; plan `penalty_rate`; line `written_off`, `payments[]` (from `installment_payment_allocations`). An ERP without them maps as before (the fields stay absent).
- `derived.missedCount` on customers; migration `customers/20261118-0001-derive-missed-installments` and the nightly `customers.recompute-derived` job fill it for documents cached before 1.14.0 (until then the API counts overdue lines). `MockErpClient` records line payments like the ERP and drops them when a payment is removed.
### Fixed
- Credit invoice line counted a write-off twice (amount and paid were too high by the write-off). The ERP adds a write-off to `amount_paid` (`DebtWriteoffService`; all 242 written-off invoices in the real data have `grand_total = amount_paid + amount_due`), so the line is now `amount = paid + due`, `paid = paid`. The 1.13.0 unit test assumed the opposite and was corrected to the ERP's numbers.
### Checked
- On the sandbox copy of the real ERP data (2026-11-15): 1,441 customers map with the new fields in 0.26 s per page of 200; colours bad 409, missed_many 80, missed_one 56, on_track 44, paid_off 852; 67 customers with an open credit invoice, 524 with an open installment invoice. Invoices imported from DiziCashier (`S-…`) have no allocation rows, so their paid lines have no payment date.

### Notes
- Exports: until 1.10.0 `format: pdf` answered `422 BUSINESS_RULE` (`export_format_unavailable`); it now builds (OD-26 closed). `targetPoisha` stays 0 for days before any target was set.
- Reconciliation reads the ERP side from the cached recent payments, so "missing in ERP" straight after posting can simply mean the cache is older than the posting; the response carries `erpFetchedAt`.
- `POST /location/points` reports off-duty points per item inside the 200 response (as `docs/openapi.yaml` declares); the batch itself is not answered with `422 OFF_DUTY`, so one late point does not make the app resend 499 good ones.
- Person names in responses stay plain strings (changing them to I18nText would break v1); clients show the string as given.
- The permission catalog in `02-requirements §3.1` is the source of truth; the "50 keys" figure in the original spec text was a miscount.
- A plan ended yesterday with 1 poisha left is suggested as bad (FR-TAG-001 has no tolerance) — see OD-25.
