# 08 — Decisions (ADR log, system-wide)

Format: **Decision · Status · Reason · Alternatives rejected · Consequences.**
Statuses: `fixed` (given by client brief, not re-opened), `accepted` (recommended by this spec), `proposed` (needs client confirmation — also listed in §3 Open decisions).
Client-repo decisions live in `admin-web/docs/08-decisions.md` (ADR-W…) and `staff-app/docs/08-decisions.md` (ADR-M…).

---

### ADR-001 Three separate repositories · fixed
- **Reason:** single-purpose repos, independent release cadence (APK vs web vs API), clear ownership for AI agents.
- **Alternatives rejected:** monorepo (Nx/Turborepo) — would simplify shared types but was explicitly ruled out.
- **Consequences:** contract sharing via `field-api/docs/openapi.yaml` + type generation; design tokens duplicated in two docs with a version number; cross-repo changes need ordered releases (field-api first, additive).

### ADR-002 Node.js + TypeScript + Mongoose; MongoDB Atlas for field data only · fixed
- **Reason:** JSON-shaped, write-heavy field data; flexible schema; time-series support for location.
- **Consequences:** money truth never in Mongo; strict TS + zod to compensate for schema flexibility; migrations still mandatory.

### ADR-003 Fastify as HTTP framework · accepted
- **Reason:** plugin encapsulation maps 1:1 to modules; schema-first validation; ~2× Express throughput; first-class TypeScript; small surface for AI agents to learn.
- **Alternatives rejected:** *Express* (no encapsulation, middleware sprawl, slower); *NestJS* (good module system but heavy decorators/DI, its own module concept would compete with our manifest, larger learning surface); *Hono* (great for edge, thinner ecosystem for Mongo/jobs).
- **Consequences:** each module exports a Fastify plugin; the manifest wraps it with feature gate and permissions.

### ADR-004 Design-first OpenAPI contract · accepted
- **Reason:** fixed decision says field-api owns `docs/openapi.yaml`; design-first lets admin-web and staff-app start against a mock server (Prism) before endpoints exist; reviews happen on the contract, not code.
- **Alternatives rejected:** *code-first generation* (zod-to-openapi) — contract would drift with implementation details and consumers could not start early; *GraphQL* — caching/offline story for mobile is more complex and not needed.
- **Consequences:** runtime validation with zod in each module; CI validates every response against openapi.yaml (conformance tests); `openapi-typescript` types for admin-web; Dart client generated or validated against examples.

### ADR-005 ERP read-model cache in field-api · accepted
- **Reason:** offline-first app needs data in its scope; Laravel must not be hammered by 100 devices; a single integration client is easier to secure and to adapt to Laravel's real schema.
- **Alternatives rejected:** *pass-through proxy* to Laravel on every request (fails when Laravel is slow/down, no offline); *apps call Laravel directly* (spreads credentials, couples apps to Laravel schema).
- **Consequences:** every value shows `erpFetchedAt`; delta sync + nightly reconcile; on-demand refresh; balances labelled "as of".

### ADR-006 field-api issues its own tokens (JWT access + rotating opaque refresh) · accepted
- **Reason:** field staff and managers are FOS users with FOS permissions; Laravel must not be modified; offline unlock needs app-side control.
- **Alternatives rejected:** *Laravel Sanctum as identity provider* (requires Laravel changes, couples availability); *Firebase Auth* (phone OTP costs, another vendor holding identities, RBAC still needed); *Keycloak* (operational overhead for 30–100 users).
- **Consequences:** password reset handled by admins (no email/SMS OTP needed initially); optional link to Laravel employee id.

### ADR-007 Custom sync protocol (mutation push + change-feed pull) · accepted
- **Reason:** only a handful of entity types, one-directional ownership (staff creates, server decides), money needs explicit idempotency and conflict semantics that generic sync engines hide.
- **Alternatives rejected:** *MongoDB Atlas Device Sync / Realm* (deprecated by MongoDB, end-of-life announced); *PowerSync / ElectricSQL* (another vendor/service, Postgres-centric); *CouchDB/PouchDB replication* (different DB, conflict model not money-safe); *Firestore offline* (second database, cost, no control over money flow).
- **Consequences:** `sync` module with `sync_changes` feed, cursors, tombstones, bootstrap; well-tested state machine on device.

### ADR-008 Mongo-backed job runner · accepted
- **Reason:** no extra infrastructure (Redis); jobs are low volume (sync every 5 min, nightly aggregates, outbox); leases in Mongo are sufficient.
- **Alternatives rejected:** *BullMQ + Redis* (better throughput, but a second stateful service to secure/back up); *OS cron* (no retries, no visibility); *Agenda* directly (maintenance concerns — keep an Agenda-compatible interface so it can be swapped).
- **Consequences:** `core/jobs` interface; worker process separate from API; job runs logged; can migrate to BullMQ if throughput demands.

### ADR-009 Background location on Android · proposed (OD-04)
- **Options:** (a) `flutter_background_geolocation` (Transistor Software) — mature motion detection, OEM workarounds, SQLite queue, HTTP batching; **paid licence for release builds**. (b) `geolocator` + own foreground service + `activity_recognition` + WorkManager — free, more code, more OEM testing.
- **Recommendation:** (a) if licence approved — it directly reduces risk R-4 (battery/OEM killing), which is the hardest problem in this project. Keep a `LocationEngine` interface in the app so (b) can replace it.
- **Consequences:** P2 starts with a 1-week spike on 4 OEM devices to confirm.

### ADR-010 Object storage: S3-compatible, private bucket, presigned URLs · accepted (provider = OD-18)
- **Reason:** fixed decision; presigned PUT avoids passing photos through the API; private bucket + short-lived GET URLs protect customer photos.
- **Provider candidates:** Cloudflare R2 (no egress fees — admins view many photos), AWS S3 ap-south-1, DigitalOcean Spaces (Bangalore). Recommendation: **R2** for cost, or S3 if the whole stack is on AWS.

### ADR-011 Deployment: one Docker image, `api` (×2) + `worker` (×1) · accepted (provider = OD-08)
- **Reason:** simple, cheap, horizontally scalable API; jobs isolated from request latency.
- **Alternatives rejected:** *serverless functions* (long-running jobs, Mongo connection churn, cold starts on weak networks); *Kubernetes* (overkill at this scale).
- **Consequences:** health/readiness endpoints, graceful shutdown, `PROCESS_ROLE`.

### ADR-012 Offline receipt numbers from per-device blocks · proposed (OD-01)
- **Reason:** staff must hand a receipt number to the customer while offline; it must be unique across devices and traceable to staff and date.
- **Format:** `{BRANCHCODE}-{STAFFCODE}-{YYMMDD}-{SEQ4}`; device requests a block (default 200) during sync; a gap report flags skipped numbers (fraud signal).
- **Alternatives rejected:** *server-issued only* (fails offline); *random UUID* (not human-friendly, not sequential for audit); *physical book only* (no digital trace) — kept as optional extra field.
- **Consequences:** Laravel's official receipt number stored after posting; customer SMS (proposed) shows both.

### ADR-013 Money as integer poisha · accepted
- **Reason:** no floating-point errors; JSON-safe up to 9×10¹⁵ poisha.
- **Consequences:** ERP mapper converts decimal strings; UI formats.

### ADR-014 Swappable map tile provider · accepted (provider = OD-17)
- **Reason:** fixed decision (OSM + Leaflet, swappable); the public `tile.openstreetmap.org` usage policy forbids heavy app use, so production needs a provider.
- **Design:** `TileProvider { id, urlTemplate, attribution, maxZoom, subdomains, apiKeyRef }` delivered by `/meta/app-config`; admin uses Leaflet, app uses `flutter_map` (Leaflet-equivalent for Flutter) with the same config; attribution always shown.
- **Candidates:** self-hosted **Protomaps PMTiles** Bangladesh extract on object storage (cheap, also enables offline area packs); MapTiler / Stadia / Thunderforest (managed, keyed). Google Maps only if the address-accuracy test (OD-19) proves OSM data insufficient — and then only behind the same interface.

### ADR-015 In-house feature flags · accepted
- **Reason:** needs are simple (module on/off, per branch); flags must also be sent to devices in sync; avoids another vendor.
- **Alternatives rejected:** Unleash / GrowthBook / LaunchDarkly (overkill, extra service, cost).
- **Consequences:** registry with owner and review-by date; CI warns on flags past review date.

### ADR-016 Location in a Mongo time-series collection with TTL · accepted
- **Reason:** compressed storage, efficient time-range queries, native `expireAfterSeconds` for retention.
- **Alternatives rejected:** regular collection (larger, manual TTL index fine but less compression); TimescaleDB/Postgres (second DB).
- **Consequences:** aggregates computed before expiry; `location_latest` separate for fast map.

### ADR-017 Bad-customer tag stored in FOS (overlay), optional write-back · accepted
- **Reason:** Laravel cannot be restructured; tag is a field-operations judgement.
- **Consequences:** office staff do not see it in Laravel unless E-15 write-back is added; admin export available.

### ADR-018 Field collections are never rejected for business reasons · accepted
- **Reason:** the money is physically in the staff's hand; dropping the record would hide cash.
- **Consequences:** conflict queue, inbox, notifications, resolution actions; only malformed/unauthorised/tampered requests are rejected.

### ADR-019 Search via Atlas Search (fallback: text + prefix index) · accepted
- **Reason:** Bangla and English names, phone fragments, typo tolerance; Atlas Search available on M10.
- **Consequences:** search module hides the engine; tests run on fallback implementation.

### ADR-020 Microfinance strictly separated · accepted
- **Reason:** separate business/legal entity; MRA regulation; different data subjects.
- **Consequences:** reserved module and permission namespace; separate collections prefix `mf_` and preferably separate database; cannot be enabled without legal flag.

### ADR-021 Time: store UTC, compute business dates in Asia/Dhaka (Luxon), injectable clock · accepted
- **Reason:** "today" rules (overdue, due today, promises, attendance) must not shift at UTC midnight (06:00 Dhaka).

### ADR-022 Scope-based 404 for out-of-scope resources · accepted
- **Reason:** avoid leaking existence of customers in other branches.

### ADR-023 Audit log append-only with hash chain · accepted
- **Reason:** tamper evidence for money and permission changes; DB role restricted to insert/find.

### ADR-024 Change feed lives in core · accepted
`sync_changes` + counters are written by `core/changefeed` so a module can record a feed entry inside its own transaction without depending on the sync module. Deviation from 04-architecture (feed owned by `sync`).

### ADR-025 FOS overlay inside `erp_customers`; assignments → customers · accepted
The FOS overlay (`fos.assigneeId/areaId/tag/openPromiseDates/locationOverride`) is a sub-document of `erp_customers` instead of a separate `customer_overlays` collection, so scope filters and list sorts stay one indexed query. `assignments` depends on `customers` (not the reverse) and pushes the computed primary assignee; customer scope for field staff is `fos.assigneeId` (replaces the materialized `assignment_scopes`). Modules declare full route paths and may register extension points (list enricher, detail contributor, timeline source, handover summary contributor) to avoid import cycles. ERP sync never overwrites `fos.*`.

### ADR-026 Background-location provider is a setting · accepted (2026-11-15, owner)
Free plugin by default; `location.trackingProvider = paid` switches the app to the paid plugin when its build includes it. The licence key ships in the app build (bound to the app id), never in settings.

### ADR-027 Sync mutations are declared by the owning module · accepted (2026-11-15)
`POST /sync/push` does not import business modules. Each module lists its offline mutation kinds in `syncMutations` in its manifest (entity, permission, `apply`), validating with the same zod schema as its REST route. The sync module checks the module flag and the permission, wraps every item in the idempotency store keyed by `(userId, mutationId)`, and reports per-item results. Reason: keeps module boundaries (CLAUDE.md §2.5) and makes a new offline entity a one-file change. Bootstrap snapshots only entities that declare `snapshot`: customers, plus (since 1.9.1) the working state a reinstalled app needs today: today's attendance day, visits and co-work sessions, open promises and pending pin proposals. Older history is read online; later changes arrive through pull.

### ADR-028 Reports aggregate at request time; only overdue history is stored · accepted (2026-11-16)
Staff performance, collection trends and reconciliation are computed from the source collections (indexed by business date) when asked, so a report always equals a raw query over the same period and there is no second copy to drift. The one thing that cannot be recomputed later is yesterday's overdue picture, so `overdue_snapshots` is written nightly per branch. `daily_metrics` (06-data-model §7) is deferred until a measured report is too slow; adding it later changes no API. Exports are built by a worker job with the requester's *current* scope, in CSV and a small owned XLSX writer (one flat sheet does not justify a spreadsheet dependency).

### ADR-029 Co-work: every participant gets visit credit, money is never shared · accepted (2026-11-16)
The owner asked that two or more staff can work together and that statistics, targets and performance reflect it properly. A joint visit stays **one record by the person who recorded it**, with the partners stored on it (`coWork.participantIds`, decided by the server from the session members accepted at `checkInAt`). Reports show single and co-work visits separately. For targets, each participant is credited `soloVisits + coWorkVisits × cowork.visitCredit`; the weight is a setting (0 to 1, default 1, per-branch override) so the business can later decide that a shared visit is worth less than a single one without a code change. The same stop recorded by two members of one session counts once per person. **Collections and cash are not split or shared**: the person who took the money recorded it, carries it and deposits it, so cash accountability (FR-CASH-*) and the ERP posting stay with one collector. Requests are online only (an invitation needs the other person's answer); visits work offline because participants are resolved from stored accept and leave times when the visit arrives.

### ADR-030 Daily targets as dated records; server-side Bangla PDF with HarfBuzz · accepted (2026-11-17, owner request)
**Targets.** The owner asked for daily targets. A target is never edited in place: every change (branch default, personal target, "back to the branch default") is a new `staff_targets` record with an `effectiveFrom` of today or later, and the value of a day is the latest record in force on that day (on the same day the later `setAt` wins). A personal record beats the branch default; a `cleared` record hands the person back to the default. Weekly off, holidays and approved leave have no target. So a report for a past period always shows the target that applied then, managers can plan ahead (next month's default), and the history doubles as the audit trail. Achievement is measured against the target **up to today** in a running period, not against the whole month, so the middle of the month does not look like failure. Co-work visits count with `cowork.visitCredit` (ADR-029). Targets are a planning aid only; they never block or change a collection.

**PDF.** Bangla needs a shaping engine for conjuncts (e.g. ক্ষ, স্ট্র, র্ক). fontkit was tried and shapes Bengali wrongly; a headless Chromium would add a 300 MB browser to the worker image. The export worker therefore shapes text with HarfBuzz compiled to WebAssembly (`harfbuzzjs`, no native build) and writes the PDF itself: Type0/CIDFontType2 fonts with Identity-H, the Noto Sans Bengali and Noto Sans subsets embedded (SIL OFL, `assets/fonts/`), each text item wrapped in `ActualText` so copy and search give the real Bangla text. A4 landscape, header repeated on every page, at most 10,000 rows. HarfBuzz is imported lazily, so the API process never loads it.

### ADR-031 Map pins: managers set directly, staff pins for pinless customers apply at once · accepted (2026-11-17, owner request)
The owner asked that admins and staff can set a customer's coordinates by dropping a pin on a map, the way a ride app picks a pick-up point, mainly for customers that have no coordinates, and that staff can add pins too. Until now a pin could only come from a staff member standing at the customer (GPS ≤ 30 m) and a manager had to approve it. Decisions: (1) a manager with `customer.location.approve` may set a pin directly (`POST /customers/{id}/location`); it is stored as an already-approved `location_proposals` record with `direct: true`, so pin history, the customer timeline and the "approved" list need no new collection. (2) Staff proposals gain `method: map` (point picked on the map, not held to GPS accuracy) and `deviceGeo` (where the phone was) so the reviewer sees the distance. (3) **Owner decision on the card 2026-11-17:** a staff pin for a customer without a usable pin (`missing`, `invalid`, `suspect_swapped`) is applied at once; moving an existing pin still waits for a manager. It is the per-branch setting `customers.staffPinApproval` (`when_missing` default, `always` to review every pin); a mock phone position never applies at once. (4) Any applied pin (approval, auto, direct) emits `customer.placed`, so polygon areas and the primary assignee are recomputed; before 1.11.0 an approved pin waited for the next area edit. Risk accepted by the owner: a pin auto-applied from the field is not reviewed first; managers see it in the approved list marked "applied at once" with the phone distance, and can move it.

### ADR-032 Leave, holidays, shifts and notices finished for the screens · accepted (2026-11-17, owner request)
The owner asked for the leave, holiday calendar, shift and notice screens in the app and the admin panel (items 6 and 7 of the 2026-11-17 list) and the guarantor call button (item 8). The server already had most of it; contract 1.12.0 fills the gaps found while designing the screens, all additive. (1) **Leave cancel:** the overlap rule blocked a staff member who typed wrong dates until a manager rejected the request, so the requester may now withdraw a pending request (`cancelled`); a decided request cannot be cancelled by staff (a manager handles changes to approved leave). (2) **Holidays:** a holiday entered by mistake can be deleted (hard delete, audited with the old value), so the list now carries `id`; a second holiday on the same day for an overlapping set of branches is refused, and the scope must match the type. Days already finalised are not re-derived. (3) **My shift:** the phone did not know which shift applied to the staff member, so `GET /attendance/me/shift` resolves it the same way attendance does. (4) **Notices:** "read" is a sync mutation (`broadcast_ack`) so it works offline like everything else in the app; the time kept is the phone's tap time, clamped between sending and receipt so a wrong phone clock cannot claim an earlier read. Managers see who has and has not read a notice (not read first) to follow up. (5) **Guarantor calls** are logged as contact attempts with `target: guarantor`; the guarantor's number is never stored in the log.

### ADR-033 A FOS plan is an ERP invoice; field-api follows the real ERP rules · accepted (2026-11-18, owner request)
The owner asked to align the three apps with the real Laravel ERP without changing the ERP, which is in production, and to document it so the ERP API can be added later. The ERP was read and its data loaded into a private sandbox copy; the field API was written there as additive files and tested against the real data (erp-findings.md, erp-integration-spec v2). Decisions: (1) **Plan = invoice.** The ERP records payments against `sales_invoices` (installment or credit sale), one installment plan per installment invoice, so `erpPlanId` is the invoice id and the ERP plan id is kept as `erpInstallmentPlanId`. A credit sale is a plan with one line on its due date. (2) **Outstanding = the invoice's `amount_due`**, the number the ERP's own payment form checks; the stored customer balance is ignored. (3) **Schedule:** line amount = due + late fee, paid from the ERP, status computed by FOS (the stored status is stale); lines the ERP's roll-forward job zeroed are kept with `rolled: true` and hidden by the apps; overdue uses the ERP report's definition (unpaid on lines due before today). (4) **Not collectable:** returned → `closed`, cancelled → `cancelled`; both are left out of totals. (5) **Posting** goes through the ERP's own `PaymentService` with every office rule: no overpayment, collector employee required (`COLLECTOR_NOT_LINKED` if the staff user is not linked), a method of that type at the branch (`METHOD_NOT_AVAILABLE`), one payment per installment invoice per day (`DUPLICATE_SAME_DAY`, OD-27), back-date window (OD-28; the owner later chose no window). (6) **Removal** in the ERP is a hard delete; the API reports it from the audit log and FOS shows the payment as reversed. (7) **Branches:** warehouses are synced too (26 customers' latest invoice is on one); branch coordinates are set in FOS. (8) The ERP repository stays untouched until the owner decides to install the prototype (spec §8); field-api runs the same code paths against the mock today.

### ADR-034 Vercel serverless for test deployments only · accepted (2026-11-18, owner request)
The owner wants to deploy and try the API before choosing the real host (OD-08). ADR-011 stays for production. For tests, `src/app/serverless.ts` caches the Mongo connection and the built app per function instance and hands each request to Fastify; `api/index.js` serves every route through a rewrite in `vercel.json`. The worker becomes `api/cron.js`, protected by `Authorization: Bearer CRON_SECRET` (constant-time compare): one call runs the jobs whose schedule matches that minute (Mongo leases, ADR-008, keep overlapping calls safe) or one named job, then drains the outbox in batches of 5 until 40 s after the call started (jobs included, so a call stays under the 60 s limit). JWT keys are required (ephemeral keys would differ per instance). **Accepted limits:** in-memory rate limits per instance, cold starts, outbox delay until the next cron call, 60 s per function, Atlas open to all IPs. Not for production money.

### ADR-035 Map pin colour = payment state; missed installments survive the ERP roll-forward · accepted (2026-11-18, owner request)
The owner asked for Google-Maps-style pins coloured by how a customer pays: red for a bad flag or a "full cycle" overdue, orange for several installments due but not a full cycle, yellow for one missed date, green for paid. **Reading chosen:** "full cycle" = the whole plan term (the ERP's "plan maturity", `SalesInvoice::finalInstallmentDueDate`): the final due date has passed and money is left — the same rule as the bad-customer suggestion (FR-TAG-001). For a credit sale the term is its one due date. "Bad flag" = a FOS tag with severity `bad` or `legal` (a `watch` tag alone does not turn a pin red). Added: blue = due today with nothing missed, grey = nothing left to pay; green = everything due so far is paid. **Missed installment:** a past-due line with money left; because the ERP's daily roll-forward job zeroes a missed line and adds its balance to the next line, a zeroed past line also counts while the line that took its balance is still unpaid (otherwise a customer who missed two months would look green until the next date). A rolled line that had been part-paid cannot be told from a paid line and is not counted. The state is computed in `customers/domain/status.ts` (`payState`, worst first) and stored as `derived.missedCount` so the list and map can filter it. Rejected: the ERP risk grade as the colour (it is a monthly-late score, not what the owner described) and a fixed number of days per colour (plan frequencies differ: daily, weekly, monthly).

### ADR-036 Deleting a pin is an overlay, and the manual ERP sync is time-boxed · accepted (2026-11-18, owner request)
The owner asked that an admin can delete any customer's map pin, and that the admin panel has a working "Sync from ERP" button. **Pin delete:** `DELETE /customers/{id}/location` sets `fos.locationOverride = { cleared: true }` and removes `location` instead of erasing data, because the ERP is the owner of its coordinates and the ERP sync rewrites `location` on every run; without the override the old pin came back at the next 5-minute sync. The ERP coordinates stay in `erpLocation`; a new pin (manager, or staff under `customers.staffPinApproval`) replaces the override. Deleting uses the permission of setting a pin (`customer.location.approve`, super admin and branch manager) and is audited as `customer.location.cleared`. Pending staff proposals stay pending. **Manual sync:** `POST /system/erp-sync` (new permission `erp.sync`) runs the delta sync with a 40 s budget because the Vercel test deploy stops a function at 60 s and no worker runs there (ADR-034): a first full pull of about 1,400 customers needs several calls, so the run saves `resume` per branch and answers `partial: true`; the button calls again. One run at a time through a Mongo lock, so a double click or two admins cannot start two pulls. The scheduled job honours the same `resume`. Rejected: one long request (times out on Vercel), per-branch sync (the ERP calls are cheap and the watermark is per branch anyway), a separate worker queue (production already has the 5-minute job).
### ADR-039 Files in MongoDB when the host has no S3 · accepted (2026-11-18, owner report)
On the Vercel test deployment (ADR-034) there was no S3, so storage was in memory: each function instance had its own files and the upload URLs were `memory://`, which no phone can PUT to. The attendance photo never uploaded, the held work-in never reached the server, and the server then refused every location point as off duty, so the live map stayed empty. **Decision:** a third storage driver `db` keeps files in the `storage_objects` collection and serves them through `PUT|GET /api/v1/storage/o?t=<grant>`. The grant (key, method, expiry, and for PUT the content type, size and sha256) is signed with an HMAC key derived from the JWT private key, which every instance shares; URLs expire after 5 minutes, like presigned S3 URLs, and the API never puts a bearer token in them. Chosen automatically on Vercel when no S3 is configured, or with `STORAGE_DRIVER=db`. **Limits:** files count against the Atlas quota (about 250 KB per photo; a free M0 cluster has 512 MB), no thumbnails, no lifecycle rules. Production keeps S3/R2 (private bucket); set `S3_*` and the driver switches back to S3. Rejected: Vercel Blob (public URLs, a second vendor) and keeping the in-memory store (broken across instances by design).
### ADR-040 Attendance is sent at once; its photo follows · accepted (2026-11-19, owner request)
Since staff-app 0.4.0 the app held an attendance event until its photo was uploaded, so the server would get the event with the photo. When the upload failed (no S3 on the Vercel test, a wrong `PUBLIC_BASE_URL`, a weak network) the event never arrived: attendance showed "waiting", the server treated the person as off duty and refused every location point (FR-LOC-001). The owner: "location coordinates must keep going every few minutes; whether the image uploads or not does not matter". **Decision:** the app sends every attendance event at once, without waiting for the photo; the server flags it `no_selfie` as before (FR-ATT-001 never rejected an event over a photo). When the photo is confirmed, the app sends the sync mutation `attendance_selfie { eventClientId, selfieMediaId }`, which links it and removes the flag. A photo already on the event is never replaced. Storage links are also built from the host the request came in on, so a wrong `PUBLIC_BASE_URL` cannot break uploads; `PUBLIC_BASE_URL` is only the fallback. `/system/health` shows the storage driver. Rejected: dropping the photo requirement (the owner still wants the photo when it works) and retrying the held event on a timer (still blocks location while the upload fails).
### ADR-041 Rough GPS points are kept for the live map; the work-in position stands in until the first point · accepted (2026-11-19, owner report)
Indoors a phone reports 100–500 m. FR-LOC-003 dropped every point worse than `location.maxAccuracyM` (50 m), on the phone and on the server, so a staff member on duty in an office or a shop never appeared on the live map. **Decision:** keep such points up to 5 km, flagged `lowAccuracy`; they update the live marker (drawn as approximate) but never the route, stops, distance or the speed reference. A rough point does not replace a good marker younger than 5 minutes. Until the first point of the day arrives, the marker is the position of the person's last attendance event (`source: attendance`). Duty rules are unchanged: nothing off duty is stored. Rejected: raising `maxAccuracyM` (a 300 m fix would then draw false distance on the route) and storing the work-in as a location point (it is already kept with the attendance event).

### ADR-042 Phone numbers added in the field stay in FOS · accepted (2026-11-21, owner request)
**Context.** The ERP sends one main number per customer (plus the few in `phone_numbers`). Staff at the door learn other numbers (wife, shop, son) and the owner wants staff and admins to save several at once and to see which number is the ERP's and which was added. **Decision.** Added numbers live in the customer overlay (`erp_customers.fos.extraPhones`: number, label, who, when). The ERP sync writes only the ERP-side `phones` field, so it can never erase them, and nothing is written back to the ERP (same rule as map pins, OD-29; write-back stays an owner decision, default no). The API returns one merged list, ERP numbers first in ERP order so `ContactAttempt.phoneIndex` keeps pointing at the same ERP number, then the added ones oldest first; `phoneDetails` says `erp` or `field` for each. If the office later types the same number into the ERP it is shown once, as the ERP's. Rules: Bangladesh mobile numbers only, normalized to `01XXXXXXXXX`; duplicates skipped (so the call is idempotent without a key); at most five added numbers per customer; an ERP number cannot be removed in FOS (`PHONE_FROM_ERP`). One permission `customer.phone.manage` (super admin, branch manager, field staff). The audit log keeps the count and the last four digits only (numbers are personal data, CLAUDE.md §3). **Consequences.** Additive contract 1.23.0, one optional overlay field, no migration. Removing a number is online-only for now (adding works offline through the sync mutation `customer_phone`).

### ADR-070 Tag reasons reach phones by re-sending tagged customers through the feed, not by a resync floor · accepted (2026-11-26, owner request)
**Context.** Staff-app schema 20 (staff-app PR #61) stores `customers.tag_reason_code` to colour the bad-tag border per reason (FR-TAG-009). Phones never stored `tag.reasonCode` before, so a customer tagged by someone else that is already on the phone shows only the generic colour until the server sends it again. Every device must re-receive those customers once, without losing or holding back unsent data (staff-app CLAUDE.md §2.3), customers only.
**Decision.** Migration `customers/20261126-0002-refeed-tagged-customers` writes one change-feed entry per customer whose tag is `tagged`, with the same audience as a tag change (`customerFeed`: assignee, plus every device of the branch where staff see it whole). Phones receive them as ordinary upserts on their next `GET /sync/pull`; each loader still applies the caller's scope. Only `tagged` customers carry a `reasonCode` in the sync payload (`tagView`), so untagged and pending customers are not re-sent. The migration runs once (`migrations_changelog`); re-running it would only re-send the same customers.

Devices offline longer than the 30-day feed window bootstrap anyway (existing rule). ### ADR-069 In the staff app every role is device-bound except the super admin; logout ends only that phone · accepted (2026-11-26, owner request)
**Context.** The owner wants only the super admin account to be used on several phones at once; every other role (field staff, area manager, branch manager, viewer and any role added later) is limited to one phone. Device binding read `devices.bindRoles` (default `["field_staff"]`), an allow-list: a new role would be unbound until someone edits the setting, and area managers, branch managers and viewers were unbound (ADR-065 (6), OD-36). Logout revoked **all** of the user's tracking tokens (ADR-067), so a super admin logging out on one phone stopped live location on the others.
**Decision.** (1) New setting `devices.multiDeviceRoles` (json, array of role names, validated against the role list, default `["super_admin"]`). On `client: app` a user is bound when their role is **not** in it (`devices.isDeviceBound`). The default applies on deploy with no migration and no settings edit (the key is new, so nothing is stored). (2) `devices.bindRoles` is **deprecated**: still defined and listed by `GET /settings` so old readers do not break, no longer read; a stored value has no effect. (3) Web logins stay unbound. Approval stays `device.manage`, `devices.maxPerUser` stays 1. (4) A user of a newly bound role may already have several active device rows (the push-token registration makes one per phone). At login from one of them, that phone keeps its place and the others beyond `devices.maxPerUser` (least recently seen first) are unbound, their sessions and tracking tokens end, and it is audited `device.unbound` with reason `device_limit`; their next login is a pending device (403 `DEVICE_NOT_APPROVED`). A login from a phone with no row while another row is active is a pending device, as for field staff. Sessions that never log in again are not cut on deploy (binding is enforced at login, as before). (5) Logout revokes the tracking tokens of the caller's session and of the caller's device only; the user's other phones keep their sessions and tokens. Tracking tokens already rotate per user and device. Contract 1.51.0 (descriptions only; 1.50.0 is taken by another change).
**Alternatives rejected.** *Change the `bindRoles` default plus a migration that rewrites the stored value when it equals `["field_staff"]`* (still an allow-list: every new role needs a settings edit or another migration; the deny-list matches the owner's rule "everyone except the super admin"). *Bind when in `bindRoles` OR not in `multiDeviceRoles`* (two settings that both decide; adding a role to `multiDeviceRoles` would silently not work for `field_staff`). *A migration that unbinds every non-field-staff device row* (logs everyone out or drops their push notifications on deploy, even users with one phone). *Hardcode super_admin* (CLAUDE.md §2.6: no role names in business logic; the owner can still list another role).
**Consequences.** Area managers, branch managers and viewers who use the staff app on two phones: the first phone they log in with after deploy stays, the second is logged out at that moment and needs approval. Supersedes ADR-065 (6) and OD-36's device part.
### ADR-068 Returned invoices are stored apart and never shown; status `closed` keeps its meaning · accepted (2026-11-26, owner request)
**Context.** The owner wants invoices returned in the ERP gone from the admin panel and the staff app. The ERP already sends invoice status `returned`; the mapper folded it (with `draft`) into plan status `closed`, so clients could not tell a return from any other closed invoice, and returned invoices still showed in the customer detail, the invoice counts and the invoice-number search (#46). No ERP change is allowed (read only).
**Decision.** (1) The mapper keeps `status: closed` for a return (changing an /api/v1 enum is not additive, CLAUDE.md §2.10) and adds `returned: true` to the plan; the ERP status is also kept in `invoiceStatus` (since 1.14.0). (2) `customers.upsertFromErp` splits the ERP plans: returned ones go to `erp_customers.returnedPlans`, everything else to `plans`, and `derived` is computed from `plans` only. Every read, filter, aggregate, search and sync payload already works on `plans`, so they all leave returned invoices out without a filter of their own, and a reader added later cannot leak them by forgetting one. (3) The customer stays, even with only returned invoices (owner's choice). (4) Sync: the `customer` item already carries the complete `plans` list; since 1.50.0 it also carries `returnedPlanIds`, so an app that keeps plans in their own table deletes them explicitly instead of relying on a full replace. (5) Migration `customers/20261126-0001-set-aside-returned-plans` moves returned plans cached before 1.50.0 (flag or stored `invoiceStatus`), re-derives, bumps `version` and writes a change-feed entry per customer, so phones receive the update on their next pull without a resync. Idempotent: it selects only documents that still have a returned plan in `plans`. Plans cached before 1.14.0 have no `invoiceStatus`; they are fixed by the next ERP read of that customer.
**Alternatives rejected.** *Keep returned plans in `plans` with a flag and filter every read* (about ten query sites incl. aggregates and other modules' `CustomerRef.plans`; one missed filter shows a returned invoice). *A new status value `returned`* (changes the meaning of `closed` and the enum in /api/v1; needs /api/v2). *Delete the plan* (loses the distinction the owner asked to keep and the ERP data for later decisions).
**Consequences.** Contract 1.50.0, additive (`CustomerDetail.returnedPlanIds`; descriptions). ERP payments linked to a returned invoice are not touched (money history, CLAUDE.md §2.1; see OD-38). A field collection the phone recorded against a returned invoice before it synced is still accepted and goes to the ERP like any other; the ERP answers `PLAN_CLOSED` and FOS makes a conflict (never dropped, ADR-018).

### ADR-067 A tracking token for the native location service, not a shared refresh token · accepted (2026-11-26, owner report)
**Context.** Live location froze on the admin map whenever the staff app was closed. The app's native Android foreground service (`LocationTrackingService`) keeps running after the app is swiped away and posts `/location/points` every 2 minutes with the access token the Dart side stored. Access tokens live 15 minutes and nobody refreshes them while the app is closed, so every upload after that is 401 and the points wait on the phone. The native side must not refresh: refresh tokens rotate and reuse detection revokes the whole family (FR-AUTH-002), so two refreshers race and the user is logged out.
**Decision.** (1) `POST /location/tracking-token` issues an opaque random token (`trk_` + 32 random bytes, base64url); only its sha256 is stored (`tracking_tokens`). Only for a staff app session with a device id (else 403 `APP_ONLY`) and the permission that lets a user post points (`attendance.record`); a tracking token cannot issue one. (2) The token is bound to user + device + **session**, and lives `location.trackingTokenTtlHours` (default 24, clamped 1–168). Binding to the session means every way a session ends (logout, admin "end session", refresh-token reuse, password change/reset, deactivation, device unbind or replacement) also ends the token, even a path added later; those paths also mark the tokens revoked explicitly and audit it (`auth.tracking_token_revoked`, one entry per user, with the reason). (3) Every call rotates: the previous token of the same user and device is revoked at once (strict, no grace period; the native service re-reads the stored token before each upload). Issue is audited (`auth.tracking_token_issued`, with the count replaced). (4) `Authorization: Tracking <token>` (a separate scheme, so a JWT parser never sees it and a leaked token is never mistaken for a bearer token). A route **opts in** with `trackingAuth` in its route options; the core auth hook resolves the token only for such a route and every other route answers 401 `UNAUTHENTICATED` `details.reason: TRACKING_TOKEN_NOT_ALLOWED`; the guard refuses a tracking-token user on any route that did not opt in as a second check. Only `POST /location/points` opts in. (5) On that route the token must be live (else `TRACKING_TOKEN_INVALID` / `TRACKING_TOKEN_EXPIRED`), its session live on the same device, the user active, and the device not pending / unbound / someone else's (`devices.deviceAllowed`). The permission guard, feature flag, `mustChangePassword`, device match of the body and the duty-hours filter all apply unchanged, so a tracking token adds no rights. (6) The token is resolved in the `onRequest` hook, so the global rate limit keys it by user like an access token. (7) The token lives in `auth` (it owns credentials, hashing and every revoke path); `location` owns the route, the setting and the policy (who, how long, device check) and calls `auth`'s public functions.
**Alternatives rejected.** *Let the native service refresh* (rotation race, family revocation, user logged out). *Longer access tokens* (weakens every route; a stolen token opens the whole API). *A scoped JWT* (cannot be revoked before expiry without a lookup, and we need the session/user/device check on every upload anyway; an opaque token is one indexed lookup). *A dedicated header (`X-Tracking-Token`)* (equivalent; the `Authorization` scheme keeps one place for credentials and keeps it out of proxies' and loggers' default header captures). *A grace period for the previous token after rotation* (the native service re-reads storage before each upload; a 401 leaves the points buffered for the next cycle, so nothing is lost).
**Consequences.** Contract 1.49.0, additive: one route, one security scheme, `401`/`403` documented on `/location/points`. The staff app must get a token at login, on app start and before it expires, and hand it to the native service; the native service must never send it anywhere else, must keep points buffered on 401 and must not refresh. A token leaked from the phone can post points for that user and device for at most a day, only on duty, and never read anything.

### ADR-066 Requests / tickets: two queues by permission, an append-only timeline, recipients without role names · accepted (2026-11-24, owner request)
**Context.** Staff need a traceable way to report, inform or ask from the app. Regular items go to area managers, very important ones to the super admin; area managers resolve or forward up; the super admin and area managers forward or assign to anyone. Every action must be traced. CLAUDE.md forbids role names in business logic, yet "area manager queue" and "super admin queue" sound like roles.
**Decision.** (1) New module `requests` (flag `module.requests`, default off) with one collection `requests`. (2) A request has a **level** (`area_manager` | `super_admin`: who is responsible; set by `priority`, changed only by forwarding to a queue) and a **currentQueue** (`area_manager` | `super_admin` | `assignee`: where it waits now) plus `assignee`. Assigning to a person keeps the level, so an item the super admin hands to a staff member is still the super admin's to close. (3) The queues are **permissions**, not roles: `request.manage` works the area manager queue, `request.important.manage` (super admin only by default) works the super admin queue. Moving, resolving or closing an item at super admin level needs `request.important.manage`; the assignee may resolve what was given to them; the creator may reopen or withdraw (close) their own. (4) Recipients: super admin queue = holders of `request.important.manage`; area manager queue = holders of `request.manage` who do not hold `request.important.manage`, else (no area manager yet) the super admin queue. The requests module computes them and puts `toUserIds` in the event; notifications only delivers. (5) The timeline is append-only (`$push` only), one entry per action with actor, time, note, from/to and status change; every action is also audited (`request.created/commented/forwarded/assigned/resolved/reopened/closed`). (6) Offline-first from the app: sync mutations `request` (idempotent by clientId) and `request_comment` (idempotent by the comment clientId, finds the request by id or by its clientId); entity `request` goes to the creator and every (former) assignee, so a request taken away arrives as a delete. (7) An item waiting in the super admin queue opens an inbox item `request.important` addressed to `request.important.manage` (no branch, so branch managers do not see it); it closes when the item leaves that queue. (8) Statuses `open | in_progress | forwarded | resolved | closed | reopened` as asked: forward → forwarded, assign → in_progress, resolve → resolved (note required), reopen (resolved/closed only) → reopened, close → closed.
**Alternatives rejected.** *One `request.manage` key and role checks for the super admin queue* (role names in business logic; no way to give the super admin queue to a deputy). *Reusing `tasks`* (tasks are office → staff with verification; requests are staff → office with routing and escalation; mixing them would complicate both). *Editable timeline entries* (the owner wants a trace; corrections are new comments). *Branch managers in the queues by default* (the owner named area managers and the super admin; a branch manager can be given `request.manage` by override).
**Consequences.** Clients key the UI off permissions: `request.manage` shows the area manager queue actions, `request.important.manage` the super admin queue. A branch manager sees and comments on the requests of their branches (`request.view`) but does not move them by default. Viewers see and comment. Field staff see only their own and the ones assigned to them now.

### ADR-065 Area manager: a role with every-branch scope and a catalog column, closed to user/role/flag/settings management · accepted (2026-11-24, owner request)
**Context.** The owner wants a "secretary-style" second-most-powerful admin: all branches, sees all the work, resolves most things, forwards to the super admin; never creates or edits users, changes roles or resets passwords; feature flags and system settings stay with the super admin. Roles were `super_admin | branch_manager | field_staff | viewer`; scope was "super admin → all, everyone else → `branchIds`", written as `isSuperAdmin(u)` in about 30 places.
**Decision.** (1) New role `area_manager`. (2) **Scope is a role-level rule**: `core/security` has `ALL_BRANCH_ROLES = ['super_admin', 'area_manager']` and `hasAllBranches(u)`; `branchFilter`, `branchQuery`, `canSeeBranch`, `sharesBranch` and every former scope use of `isSuperAdmin` go through it. `branchIds` of an area manager is only the home branch (where their own records belong). Listing every branch in `branchIds` was rejected: a new branch from the ERP would silently be out of scope until someone edits the user. (3) **Permissions come from a catalog column** (AM in 02-requirements §3.1, `defaults.area_manager` in the manifests): everything the super admin holds by default except `user.manage`, `rbac.manage`, `flag.manage`, `settings.manage` (never), and `cash.limit.manage`, `media.delete`, `request.important.manage` (off, can be granted per user). The area manager does **not** short-circuit like the super admin: overrides still apply. (4) **`neverFor`**: a permission may list roles that never hold it; evaluation denies before any override and an `allow` override is refused (422 `PERMISSION_NOT_GRANTABLE`). `user.manage`, `rbac.manage`, `flag.manage` and `settings.manage` are `neverFor: ['area_manager']`, so "must not" is enforced, not just a default. `check:permissions` checks that `neverFor` matches `—` in the docs column. (5) Only a super admin creates, edits, re-roles, resets or deactivates super admins, area managers and branch managers (`OFFICE_ADMIN_ROLES`), even if a branch manager is given `user.manage`. (6) **Device binding:** `devices.bindRoles` stays `["field_staff"]`; area managers log in from the web and, if they use it, from the app on any phone without device approval (like branch managers and the super admin). The owner can add `area_manager` to the setting to bind them. *(Superseded by ADR-069, 1.51.0: every role except `devices.multiDeviceRoles` is bound.)*
**Alternatives rejected.** *A super admin with overrides denying user management* (super admin short-circuits evaluation; the last-super-admin rule and the "manage SA accounts" rules would apply; easy to undo by mistake). *Branch manager with every branch listed* (see 2; also branch managers cannot be closed to user management by default). *Hard-coded `role === 'area_manager'` checks in routes* (CLAUDE.md §2.6).
**Consequences.** A new role is one line in `ROLES`, one in `ALL_BRANCH_ROLES` if it sees everything, and one catalog column. Field-staff-only rules (`role === 'field_staff'` own scope) treat an area manager as office, which is intended. `/rbac/permissions` returns `neverFor` so admin-web can grey out the toggle. Because they hold their keys in every branch, area managers also receive the branch-addressed notifications and inbox items of those keys (tag reviews, leave requests, device approvals, …) for every branch, like the super admin; a per-user deny override narrows that. On the app, their bootstrap covers every branch, like the super admin's.

### ADR-064 Login throttling locks accounts, not offices; a known device passes an IP lock; device approval stays manual · accepted (2026-11-24, owner report)
**Context.** Staff saw "account blocked" at login. `login()` locked both `acct:<phone>` and `ip:<ip>` after 5 failures in 15 min. All staff in one office or on one mobile carrier NAT share an IP, so 5 wrong passwords from anyone locked them all for 15 min. Without `TRUST_PROXY` on Vercel, every request looked like it came from Vercel's proxy IP. Separately, a field staff on a new phone, or on an old build with a random per-install device id after a reinstall, gets 403 `DEVICE_NOT_APPROVED` until a manager approves (FR-AUTH-007). The owner wants device binding, but not repeated approvals or lockouts.
**Decision.** (1) The account lock stays at 5 failures / 15 min. (2) The IP lock threshold is the setting `auth.ipLockFailures` (default 50 / 15 min; 0 turns it off). (3) While an IP is locked, a user still logs in if the request comes from a device or browser that already had a session of theirs: a `sessions` row with the same `userId` and `deviceId` (the app's `X-Device-Id`), or admin-web's `fos_rt` cookie matching one of the user's sessions. Everyone else behind that IP gets 423 `scope: ip` before the password is checked, so a locked IP gets the same answer for right and wrong passwords and learns nothing. (4) `TRUST_PROXY` defaults to true when `VERCEL` is set. (5) 423 carries `until`, `retryAfterSec`, `scope` and `Retry-After`; 403 `DEVICE_NOT_APPROVED` carries `pendingDeviceId`. (6) Device approval is never automatic. `likelyReinstall` on a pending device (same model and Android version as the only active device, which was idle for `devices.reinstallHintIdleDays` days, default 0 = off) is only a hint for the admin. Approving is idempotent and replaces the least recently seen active device.
**Consequences.** One person's typos lock only their own account. An attacker guessing across accounts from one IP is still stopped after 50 failures, unless they also hold a victim's device id or refresh cookie. In that case only the per-account lock (5 / 15 min) applies, which is the same protection as before for a single account. `X-Device-Id` is not secret, but ANDROID_ID is not visible to other people. Recognising a device uses the `sessions` collection (rows live until the refresh token expires), so a phone that has not logged in for longer than the app refresh TTL is no longer "known". **Rejected:** letting any correct password through an IP lock (makes the IP lock an oracle, useless against credential stuffing); dropping the IP lock (no defence against stuffing); auto-approving a "same model" device (model and Android version are not unique; the owner wants an admin decision).

### ADR-063 The Mongo connection pool is bounded per process and closes idle connections · accepted (2026-11-24, owner report)
**Context.** Atlas once refused new connections because the cluster's connection limit was reached, and the database stopped answering. On Vercel (ADR-034), every function instance (`api/index.js` and `api/cron.js` separately) keeps its own Mongoose connection. `connectMongo` set no pool options, so the driver default applied: up to 100 connections per instance, plus monitoring sockets per replica-set member, and idle connections were never closed. Several requests run queries in parallel (`Promise.all`), for example the dashboard, sync and ERP import. In busy hours (many staff syncing or a first load after an install, admin pages, the 2-minute ERP sync), Vercel runs many instances, and their pools together reached the Atlas limit (500 on M0). Frozen instances also keep their sockets counted until Atlas drops them.
**Decision.** `mongoOptions()` sets `maxPoolSize` (config `MONGODB_MAX_POOL_SIZE`, default **10**, 1–100), `minPoolSize: 0`, `maxIdleTimeMS` (config `MONGODB_MAX_IDLE_MS`, default **60 000**) and `waitQueueTimeoutMS: 15 000`. The API, the worker, the CLI and the serverless adapter all connect through it.
**Consequences.** Total connections stay near instances × 10 instead of × 100. A request that finds all 10 busy waits a few milliseconds for a free one; 10 is far above what one request needs (2–5). An idle instance drops to monitoring sockets after a minute. Both limits can be changed through environment variables without a release. Turning on Vercel Fluid compute (several requests per instance) lowers the instance count further; that is the owner's setting. **Rejected:** a higher Atlas tier alone (the pools would still grow with instances); one shared connection per request (slow cold queries, no parallel queries).

### ADR-062 The customer list pages by offset up to 1000 rows, with an exact total · accepted (2026-11-23, owner request)
**Context.** The admin customers page offers page sizes 100, 500 and 1000 with a numbered pager (jump to page N). `GET /customers` allowed 200 rows and only a cursor, so the admin stitched 500/1000-row pages and jumps out of 100-row cursor calls; `total` was capped at 10,000, so a pager could not reach the last page of a large branch set. **Decision.** Additive 1.46.0: `limit` ≤ 1000 and an optional 0-based `offset` that wins over `cursor` (the cursor already held an offset, so both share one code path and `nextCursor` is unchanged). `total` is the exact count. Cost is kept down by (1) a projection of only the fields a list row needs (a customer document carries every plan's schedule), and (2) one index per sort, `branchId`-prefixed for scoped users and sort-only for the super admin; every sort ends with `_id`, so offsets are stable. Rejected: keyset (seek) pagination — it cannot jump to page N; an estimated count — wrong numbers on a pager; a new endpoint — the existing one only needed two limits relaxed. **Consequences.** A deep offset is a skip over index keys (fine at the expected 10k–100k customers); a row that changes between two calls can move between pages, as with any offset pager. `sort=distance` still sorts the nearest 2000 in memory.

### ADR-059 A promise follow-up is a new linked promise; broken stays broken · accepted (2026-11-23, owner request)
**Context.** After a broken promise staff make a new promise with the customer; the office wants to see the chain and who was never followed up. Options: re-open the broken promise (loses the verdict and the fulfilment rate), edit its date (same), or a new promise linked to it. **Decision.** Promises stay immutable in their verdict. A follow-up is an ordinary promise (same REST call and sync mutation `promise`, idempotent by clientId) with `followUpOf`; the server stores `attempt` (previous + 1) and `chainRootId`, and keeps `followUpId` on the broken one (the newest follow-up not cancelled; recomputed on cancel) so `brokenWithoutFollowUp` is one indexed query. Only a broken or partially kept promise of the same customer can be followed up (422 `PROMISE_FOLLOW_UP_INVALID`). After `promises.followUpAlertDays` (default 2) days without a follow-up the office gets an inbox item `promise.no_follow_up`, resolved by the follow-up. Office-made promises (web) are audited. **Consequences.** Rates stay honest (every attempt counts); clients draw the chain from `followUpOf` / `followUpId` / `attempt`.

### ADR-058 On Vercel jobs run from called cron ticks that catch up on missed slots · accepted (2026-11-23, owner request; amends ADR-034)
**Context.** On Vercel the worker runs only when `/api/cron` is called. Only admin-web's "Sync from ERP" (every 2 min while a page is open) was syncing; with nobody logged in nothing ran, outbox and other jobs included. A job ran only when a call landed exactly on its minute, so calls every few minutes would skip `*/2` slots and nearly every daily job. **Decision.** (1) A GitHub Actions schedule (every 5 min, `.github/workflows/cron.yml`, repo secret `CRON_SECRET`, skipped with a notice when missing) calls `/api/cron`; an external pinger every 1–2 min is recommended because GitHub schedules are late. (2) A job is due when the latest slot of its schedule within its catch-up window (default 6 h; delta sync 10 min, exports 5 min, 09:00 reminders 3 h, the 23:50 snapshot 9 min) has not run; the lease key is the slot's minute and only a newer slot can claim it, so each slot runs once across overlapping calls. (3) A call has a 40 s budget: each job gets the time left minus 8 s kept for the outbox (the ERP delta sync stops at it and resumes next call, ADR-056), no job starts with < 2 s left (its slot stays for the next call), heavy jobs (nightly reconcile) run last. `erp.delta-sync` runs every 2 minutes. **Consequences.** Daily jobs may run up to the end of their window late when calls are sparse; the nightly reconcile has no budget and may be stopped at 60 s (its lease then expires after 15 min; the next night runs again). Production (ADR-011 worker, tick every 20 s) also gains the catch-up after restarts.

### ADR-057 Every ERP customer and every invoice reaches FOS; cash sales are shown, never due · accepted (2026-11-23, owner decision)
**Context.** FOS pulled `scope=receivables`: only customers with an installment or credit invoice, and only those invoices. The owner decided that all customers and all invoices must reach the app, cash sales included. howlader-ERP PR #5 adds `invoices=receivables|all` to `GET /customers` and `GET /customers/{id}`; `scope=all` already listed every customer. **Decision.** (1) Setting `erp.customerScope` = `all` (default) | `receivables`. `all` sends `scope=all&invoices=all` (list) and `invoices=all` (single read). (2) Compatibility: a 422 to `invoices` (ERP not deployed yet) falls back to `scope=all` without it, a 422 to that to the old `scope=receivables`; the client remembers the level per process and warns once, so field-api can be deployed first. (3) The watermark belongs to a scope (`erp_sync_state.scope`, absent = receivables): when the setting differs, the branch is pulled again from page 1 and a resume of the other scope is dropped; so the first run after this release re-reads everything. (4) `Plan.kind` gains `cash` (additive enum value). A cash invoice has no schedule, is `completed` when paid and `closed` otherwise, so the existing rules (closed/cancelled ignored, no lines, outstanding 0) keep it out of due, overdue, missed, bad suggestion, open invoices, the invoice-kind filter and every due total; it counts in `invoiceCount.total`. A cash invoice the ERP still shows money on stays `closed`: the field does not collect cash sales. **Consequences.** More customers per branch (pins in grey, `paid_off`); larger first pull (several "Sync from ERP" presses on Vercel). Clients must render `kind: cash` (and unknown kinds) as a cash sale. **Rejected:** a separate entity for cash sales (the ERP sends them as invoices; one shape is simpler), making cash invoices collectable (owner asked to show them, not to collect them), a manual watermark reset (the scope on the state does it automatically).

### ADR-056 The ERP pull saves its place after every page and never stops on one bad row · accepted (2026-11-23, owner report)
**Context.** The owner's ERP has 2400+ customers/invoices; the staff app showed about 800. On the field-api side two faults could keep customers out of FOS for good: (1) the pull saved where it was only when its 40 s budget ran out after a whole page; a run the host stopped (Vercel ends a function at 60 s and the scheduled job had no budget) or a page that failed lost all its progress, and the next run began the same branch at its first page again; (2) the mapper read a page as a whole, so one row it could not read failed the page, the branch error was only logged, and every later customer of that branch never arrived. The rest of the gap is by design and was not changed: the ERP is asked for `scope=receivables` (customers with an installment or credit invoice, not every ERP customer), and field staff see only the customers of their own branches (`customers.staffVisibility`, FR-CUS-015), so one staff member never sees the whole ERP. **Decision.** Save `resume.cursor` after every page of every pull and check the budget per customer, remembering the customers of a cut page (`resume.done`) so none is done twice; read rows one by one and skip (log, count, keep in `lastSkipped`) a row that cannot be read; count failed branches; end a branch when the ERP repeats a cursor; reconcile continues past a failing branch and never marks customers missing when an unreadable row had no id. `POST /system/erp-sync` answers `skipped` and `failedBranches` (additive, contract 1.44.0). **Consequences.** One extra small write per page. A skipped row stays out of FOS until the ERP data or the mapper is fixed, but it is visible (log, `lastSkipped`, `skipped`). `pnpm coverage:report` gives the owner the counts per branch and per staff member from MongoDB, read only. The scope question became ADR-057. **Rejected:** a per-customer `try` around publishing (hides real database errors), raising the page size or budget (does not fix a stopped run), changing the visibility rule (an owner setting, not a bug).

### ADR-055 The office moves a place offline through `place_edit` · accepted (2026-11-22, owner decision)
**Context.** ADR-051 kept the direct move online only (REST `PATCH /places/{id}` with `location`): the sync mutation `place_edit` carried words and icon. The owner wants a super admin or branch manager using the staff app to move a marker at once, also without a connection. **Decision.** `place_edit` accepts an optional `location` with the same shape and validation as `PlaceUpdate.location`, and the sync handler calls the same service function as the PATCH route (`places.service.edit`), so the rules cannot drift: only `place.manage` moves (otherwise the whole item is rejected `FORBIDDEN MOVE_NEEDS_MANAGE`, nothing half-applied), Bangladesh bounds, `PLACE_DELETED`, the open move request closed as rejected, audit and events. ### ADR-054 Map places are shared landmarks for the whole area, not per branch · accepted (2026-11-22, owner decision)
**Context.** ADR-051 gave each place a branch and scoped visibility and office actions to it, like customers. The owner decided that map places (shops, markets, mosques, ghats) are landmarks of the whole area: a staff member of one branch passes the places another branch added, two branches' areas touch, and a place added by one office is just as true for the other. **Decision.** (1) A place belongs to no branch. Creating one needs no branch; a `branchId` in the body is accepted (so older clients stay valid) and ignored, and `PLACE_INVALID_BRANCH` is gone. The creator's first branch is still stored (`map_places.branchId`, null when they have none) for the record and the audit line only; the API shows it as `''` when null so `/api/v1` stays a string. (2) **No branch scope for places:** everyone with `place.view` sees every place of every branch in `GET /places`, `GET /places/{id}` and the sync entity `place` (pull loader and bootstrap snapshot). (3) Office actions (`place.manage`: edit, direct move, delete, decide move requests) work on any place; the staff rules are unchanged (edit own places, request a move of any place). Permissions stay checked by key, never by role. (4) **Who is told:** the `place.move_request` notification goes to every active `place.manage` holder in every branch (`rbac.holdersOf(key, null)`). The inbox item is one item with a new `permission` field (`place.manage`): the inbox shows an item to a user whose branches it belongs to (as before) **or** who holds that permission anywhere; the decision closes it for everyone. One item rather than one per branch, so a super admin or a manager of two branches does not see it twice. (5) **Sync:** every place change is written to the feed once per branch (`fanoutBranchId`), since the feed reaches devices by branch; a resync floor (`places-all-branches`) makes devices that snapshotted under the branch rule take one fresh snapshot, as ADR-038 did for customers. **Consequences.** Contract 1.42.0, additive (`PlaceCreate.branchId` deprecated; descriptions changed; `InboxItem` description). New index `map_places { status:1, _id:-1 }` (forward-only, idempotent index migration); no data migration. Inbox now depends on rbac (to read the caller's permissions). The feed gets one row per branch per place change (a handful of branches, small). Clients: staff-app drops the branch picker and keeps other branches' places; admin-web lists every branch's places and requests. If places ever need to be per branch again, that is a `/api/v2` change and a new ADR.

### ADR-053 On Vercel the phone's photo goes through the API straight to Cloudinary; MongoDB is the fallback · accepted (2026-11-22, owner request)
**Context.** After 1.37.0 (ADR-050) the owner set the Cloudinary keys on Vercel, but attendance photos still did not upload. Live health showed `storage: s3`, `cloudStorage: cloudinary`: the phone PUTs to the presigned S3 URL first, and only after the confirm does the outbox copy the photo to Cloudinary (and only when `/api/cron` runs). If that S3 bucket or its settings are wrong, the phone's PUT fails, the confirm answers `NOT_UPLOADED`, and nothing ever reaches Cloudinary. (From the code this is the only path that fails while Cloudinary is configured; Vercel's settings and logs were not visible.) The owner wants photos in Cloudinary first, with no new staff-app release.
**Decision.** (1) New storage driver `cloudinary` (`CloudinaryStorage`, a MongoDB store, ADR-039, with a different upload step). `presignPut` hands out the same signed `/api/v1/storage/o` link (HMAC grant, 5 minutes, content type, size and sha256 checked by the route); the phone protocol is unchanged. (2) When the bytes arrive, an image is uploaded to Cloudinary there and then (existing `CloudinaryClient`, delivery type `authenticated`, public id `<folder>/<kind>/<ownerId>/<sha256>`, 15 s limit) and a record `storage_cloud_objects { _id: key, publicId, version, bytes, format, contentType, storedAt }` is kept; the answer is 200. (3) **Fallback:** if Cloudinary fails, times out or is not configured, the bytes are kept in MongoDB (`storage_objects`) and the answer is still 200, so the phone's upload never fails; the confirm then queues `media.cloud_copy` as in ADR-050, which moves it on the next `/api/cron`. A retried PUT that reaches Cloudinary removes the MongoDB copy. Voice notes and server-side files (exports) stay in MongoDB. (4) **Confirm:** `exists()` is true for a key in either place. When the upload is in Cloudinary, the confirm writes `cloud {…}` and `baseRemovedAt` on the media row in the same update, queues **no** copy, and then drops the record (the row owns the file). (5) **Reads:** a row with `cloud` gets the signed Cloudinary download link (5 min, as ADR-050); otherwise the MongoDB store's signed GET; a key found in neither is served by the previous store. (6) **Old photos:** when `S3_*` is still configured, S3 is kept as a read/delete-only previous store: links, the copy job (which then moves those photos to Cloudinary) and admin deletes reach S3 only for keys that are neither in Cloudinary nor in MongoDB, so new photos never touch S3. Files kept in MongoDB under the `db` driver need nothing (same collection). (7) **Deletes** (FR-MED-003/004): rows with `cloud` are removed by the bulk Cloudinary delete as before; the base store is now asked only for rows whose base copy still exists (`baseRemovedAt` unset); a never-confirmed upload that went to Cloudinary is removed through its record. (8) **Turned on** by `STORAGE_DRIVER=cloudinary`, and automatically on Vercel when `STORAGE_DRIVER` is empty and the three `CLOUDINARY_*` settings are present (before S3). The owner said S3 is not set up and will not be used: S3 now counts as configured only with both `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY` (an endpoint or key id alone used to select it, the likely cause of `storage: s3` on live), and on Vercel `STORAGE_DRIVER=s3` without both keys is ignored. The S3 reader for old photos (6) is kept only for completeness; on live there are none. Elsewhere the automatic choice is unchanged. `/system/health` `storage` shows `cloudinary`.
**Consequences.** Contract 1.40.0 (additive: one enum value in health; `/storage/o` also exists under this driver). The photo passes through the function (≤ 1 MB, inside Vercel's 4.5 MB request limit); an upload takes as long as Cloudinary needs (at most 15 s before falling back). The owner must keep `S3_*` set while old S3 photos are still wanted, and keep `/api/cron` running for fallback copies. **Rejected:** uploading from the phone straight to Cloudinary (a new app release and a signature endpoint), dropping the S3 reader (old photos would break), remembering the store per media row (the key lookup order gives the same result without a migration).

### ADR-052 A pin from the app by someone who may approve pins applies at once · accepted (2026-11-22, owner request)
**Context.** Every pin sent from the staff app was a proposal; only a pin for a customer without one could apply by itself (ADR-031). A super admin or branch manager who logs into the app and moves a customer's pin therefore created a request waiting for a manager, usually themselves. The owner: an office user's pin must apply at once. **Decision.** `proposeLocation` asks the permission port whether the caller holds `customer.location.approve` **evaluated for the customer's branch only** (so a branch override that denies it there wins, and a field staff member granted the key by a user override gets it too; no role names, CLAUDE.md §2.6). ### ADR-051 Map places: anyone adds at once, only the office moves; moves by request · accepted (2026-11-22, owner request)
**Context.** OpenStreetMap has few names in the branches' areas. The owner wants any staff member to write a name on the map that stays as a marker (with a few icons to choose from) so everyone knows what is where; a staff member who wants a marker moved sends a request the office approves; the admin panel creates and changes them too. **Decision.** New module `places` (flag `module.places`, off by default), collection `map_places`. A place has one name (≤ 60), an icon from a fixed list of ten (`shop … other`; the clients draw the symbols), an optional note (≤ 200), a point and a branch (the creator's first branch unless they pick another of theirs). A direct move or a delete by the office closes an open request as rejected. Soft delete only. Offline: sync mutations `place`, `place_edit`, `place_move_request` (by server id or by the creator's `placeClientId`), sync entity `place` fanned out to the branch, bootstrap snapshot of the branch's active places. A place is not a location-tracking point (CLAUDE.md §2.12 does not apply): only the chosen marker point is stored, never the phone's position. **Consequences.** Additive contract 1.38.0; new collection and index migration; staff-app needs a local table, outbox kinds and map layer; admin-web a list page, the map layer and a request queue. Places are not shown in the staff activity feed yet (OD-33).

### ADR-050 Photos live in Cloudinary; the server's store is the fallback; admins delete photos with a log · accepted (2026-11-22, owner request)
**Context.** The owner wants every photo staff take in the company's Cloudinary account, admins able to see them, the previous months' photos deletable in one go (an alert from the 5th of the month, a typed confirmation), the attendance photos of any staff member on any day deletable with a visible log ("Deleted by admin <name>" and when), and a deleted photo gone everywhere. Without Cloudinary the hosting storage (S3 or MongoDB, ADR-039) must keep working.
**Decision.** (1) **Phone protocol unchanged:** presigned PUT to the base store, then `POST /media/{id}/confirm`; staff-app needs no release. (2) Confirm queues `media.cloud_copy` in the same transaction when Cloudinary is configured (all of `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`; folder `CLOUDINARY_FOLDER`, default `fos`). The worker reads the file from the base store, uploads it with a signed server-side REST call (no SDK: SHA-1 of the sorted parameters plus the secret), delivery type `authenticated` (never public), public id `<folder>/<kind>/<ownerId>/<sha256>`, stores `cloud { provider, publicId, version, bytes, format, copiedAt }` and then deletes the base copy (`baseRemovedAt`). A Cloudinary outage is retried with the outbox backoff (24 h); confirm never fails because of it. Only images are copied; voice notes stay in the base store. (3) **Reads** stay 5-minute links: a signed private download URL (`/image/download` with `expires_at`) for a copied photo, else the base store's presigned GET (the fallback). If Cloudinary is later unconfigured, a copied photo answers 409 `CLOUD_STORAGE_NOT_CONFIGURED` instead of a broken link. (4) **No server-side recompression:** the phone already resizes to ≤ 1280 px and compresses to ≤ 250 KB JPEG (staff-app `processPhoto`) and the API refuses > 1 MB; adding `sharp` (a native module) to the Vercel functions (ADR-034/039) was judged not worth the risk for no gain. (5) **Deletion** marks the media row `deleted { at, by, byName, reason, scope }` at once (its link answers 404 `MEDIA_DELETED`, the same file cannot be uploaded again: 409) and queues `media.remote_delete` batches of 100 in the same transaction; the request then tries the removal at once and the outbox retries what failed. Cloudinary removal uses the Admin API bulk delete (`DELETE /resources/image/authenticated`, up to 100 public ids, `invalidate=true`, basic auth) instead of one signed `destroy` per photo: a purge of hundreds of photos fits in one request. "Not found" counts as removed, so every step repeats safely. A copy that finishes after its photo was deleted removes what it uploaded. (6) `media.delete` (super admin only by default) guards `GET /media/purge/preview`, `POST /media/purge` (confirm text `DELETE <YYYY-MM>` exactly, 200 per call, client repeats until `remaining = 0`, one audit entry per call, money proofs only on request) and `POST /attendance/photos/delete` (events keep `selfieDeleted { at, by, byName }`, `selfieMediaId` becomes null). Branch scope applies if the key is granted to a manager.
**Consequences.** Contract 1.37.0 (additive). The owner sets the Cloudinary variables in field-api's environment; `/system/health` shows `cloudStorage`. On Vercel the copy waits for the next `/api/cron` call (ADR-034), so a photo is served from MongoDB for a few minutes. Photos already stored before the variables are set stay in the base store (no back-fill job; could be added). Deleted rows remain as the log; audit entries never hold photo URLs. **Rejected:** uploading from the phone straight to Cloudinary (needs a new app release and an upload preset or signature endpoint), public delivery type, hard-deleting media rows (loses the "deleted by" log).

### ADR-049 A collection goes to the ERP when it is deposited; a deposit is final; a collector with no ERP employee is posted by name · accepted (2026-11-22, owner request)
**Context.** Until 1.35.0 every collection was queued for the ERP the moment it was recorded, and a deposit was a separate cash hand-over that a manager verified or rejected (FR-CASH-004) and could delete (FR-CASH-009). In live mode a collection reached the ERP in seconds, so "edit until deposited" (ADR-047) only held while the ERP was read-only. The owner wants: staff may change their collections until they deposit; the deposit itself sends the money to the ERP, with no office confirmation; nothing about a deposit can be edited or deleted afterwards; the office only sees who took how much from whom and what was deposited. The ERP needs a referrer employee on every office payment, but not every field user has an ERP employee record, and staff work across branches.
**Decision.** (1) Recording a collection queues nothing. (2) `POST /cash/deposits` hands in everything the collector holds at once: all cash in hand (the amount must equal it, `DEPOSIT_MUST_BE_ALL`) and every mobile banking, bank or card collection not handed in yet (the owner chose that these wait for the deposit as well). The deposit is stored `submitted` with the list of collections; each collection gets `deposit {id, at}` and, if the ERP does not have it, its ERP post is queued under its own original key, all in one transaction (`collections.submitForDeposit`). A second deposit or a void racing it rolls the whole deposit back. (3) Verify, reject and delete answer 409 `DEPOSIT_FINAL`; the routes stay because /api/v1 is additive-only. The `cash.deposit.pending` inbox reminder is no longer raised (no `cash.deposit.recorded` event). (4) A deposited collection cannot be edited or withdrawn (`COVERED_BY_DEPOSIT`). (5) With ERP posting off (`record_only`), the deposited collections wait and `collections.requeue-stuck` sends them once it is on; it never sends a collection that is not deposited. (6) Cash in hand is worked out from the links; deposits from before 1.35.0 (no list) still pay off the oldest unlinked cash, minus what a migration linked to them and minus what a 1.35.0 deposit recorded as already paid (`legacyAbsorbedPoisha`), so voiding a deposited collection never moves other cash in or out of hand. The migration links each old pending/verified deposit to the cash collections it covered in full, so those go to the ERP; a collection covered only in part goes with the next deposit (its whole amount is one ERP payment). (7) The ERP field API (howlader-ERP, API files only) accepts a payment without `collector_employee_id` when `collector_name` is given: the payment's referrer stays empty (the column is nullable and the ERP's own advance payments already do this; its reports show such payments under "none") and the name is the payment reference. A given employee id must still be an active employee. field-api always sends the name, so linked staff keep the referrer and unlinked staff are posted by name. Cross-branch work needs nothing new: the ERP books a payment into the invoice branch's wallet whoever collected it.
**Consequences.** Contract 1.35.0. Old app versions that deposit part of the cash get 422 `DEPOSIT_MUST_BE_ALL` and must update. The ERP change must be deployed before or with this field-api release, otherwise an unlinked collector's payment is refused by the ERP's validation and shows as a conflict. Money truth stays in the ERP: field-api never computes a balance. The collection board (FR-REP-007) counts ERP-accepted money, so a collection counts there once it is deposited and posted. **Rejected:** a shared "Field App" ERP employee for unlinked staff (adds an HR record that payroll and attendance would see); posting at record time as before (contradicts "edit until deposit"); partial deposits (an ERP payment cannot be split across two hand-overs).

### ADR-045 The collection board is company-wide and counts verified money only · accepted (2026-11-21, owner rule)
**Context.** The leaderboard (FR-REP-005) ranks the field staff of one branch for a day or a month, counts money the moment it is recorded, needs a number of present days, and leaves out anyone who is not field staff. The owner wants one board for motivation: every person who collects, in every branch, for the month and for all time, counting only money that is verified, with managers and admins on it by their collections alone.

**Alternatives rejected.** Changing what `collected` means on the existing leaderboard (a change of meaning inside `/api/v1`); adding periods and roles to the existing endpoint (its present-days and target rules do not apply to a manager or to all time).
**Consequences.** "Verified" follows the ERP posting, so a collection appears on the board when the ERP accepts it, not when it is taken. The amounts are field-system activity, not ERP balances, and are labelled so in the clients.

### ADR-044 Break windows, overtime and late absences are derived, per branch · accepted (2026-11-21, owner request)
**Context.** The owner's branches do not share one week: Ulania is closed on Saturday and has the regular break; every other branch works all seven days and has a long Friday break (12:30–15:30). He also wants break time over the limit, overtime and "two late days = one absent day" visible. The server had one break limit per shift, no overtime, and the default shift setting accepted any JSON (the admin panel edited `duty.*` keys the server never had).
**Decision.** (1) A shift, and the default-shift setting per branch, carries weekly `breakWindows`; break time inside the day's window is free, the rest is held against `maxBreakMin`. A window is an allowance, not a rule that the break must be taken then. (2) `overtimeMin` is derived per day: duty after the shift end from `attendance.overtimeAfterMin` minutes, all work on a weekly off day or holiday, nothing after the shift end on a day the system closed (the real end is unknown) and nothing for work during approved leave. (3) `lateAbsences = floor(late days of the month / attendance.lateDaysPerAbsent)`, reported next to `absent`, never added into it. (4) The default-shift value is validated on write.
**Alternatives rejected.** A separate "Friday shift" per user: every staff member would need two shifts and a weekday rule. Replacing the break limit on a window day: a five-minute tea break on Friday morning would turn the day red. Adding late absences into `absent`: the calendar would show absent days nobody can point to.
**Consequences.** Everything stays derived from events, so a correction or a changed setting re-derives the day; closed days stored before 1.25.0 are derived once more. Pay is not computed here (OD-30).

### ADR-043 Late time is counted from the shift start · accepted (2026-11-21, owner rule)
**Context.** A work-in inside the grace (`lateGraceMin`, default 15) is on time. For a work-in past the grace the server counted only the minutes after the grace (09:40 with a 09:00 shift = 25), while the staff app counted from the shift start (40). The owner's rule: the grace decides *whether* someone is late; once late, the time is counted from the shift start. **Decision.** `lateMin = minutes from shift start to the first work-in` when that is more than the grace, else 0. The app already works this way, so the two now agree. **Consequences.** `lateMin` of late days grows by the grace from this version on; stored `attendance_days` of earlier dates keep the value they were closed with (a correction or a recompute brings the new value). No contract change: `lateMin` is still "minutes late".

### ADR-037 Admin tasks for staff: a resolve request is verified by an admin · accepted (2026-11-18, owner request)
The owner asked that an admin can give any staff member a task with a note, not tied to a customer; the staff member is notified, sends a resolve request, and the task is resolved only after an admin verifies it. **Chosen:** a new module `tasks` (flag `module.tasks`, off by default) with states `open → resolve_requested → resolved`, a reject path back to `open` that needs a reason (same rule as rejecting leave), and `cancelled`. Alternatives rejected: reuse customer notes (they are tied to a customer and immutable), reuse broadcasts (no per-person state). The assignee must be an active field staff member; the branch is stored on the task (one of the assignee's branches) so manager scope works for staff in several branches. Resolve request and verify/cancel are idempotent replays, so offline retries never fail. Notifications reuse the notification center; managers also get an inbox item until the request is decided. Assignee cannot resolve alone by design: the owner wants the admin's check.

### ADR-038 Field staff see their whole branch; staff may hold several branches · accepted (2026-11-18, owner request)
The owner wants a field staff member to see every customer of their branch even when nobody assigned them, and a staff member to work in several branches (chosen when the account is made or later). **Decision:** the customer scope of `field_staff` is every customer of `user.branchIds` (like a branch manager), switchable per branch back to the old assigned-only rule by `customers.staffVisibility = assigned`. Assignment keeps its meaning (primary assignee, "my customers", Today, targets, handovers, area rules); visits to a customer that is not one's own still carry the `not_in_scope_at_record_time` flag as information. Visits, collections and promises stay "own only" for staff. `branchIds[0]` is the home branch for everything that needs one branch (attendance, cash, targets, shift, app settings). **Sync:** a customer change is written once with `fanoutBranchId` instead of one row per device; pull reads `userIds = me OR fanoutBranchId ∈ my branches`, and each entity loader still applies the caller's scope, so a device never receives a customer it may not see (it gets a tombstone instead). Branch membership and setting changes re-send the branch's customers, so devices converge without a full resync. **Rejected:** writing one change row per staff member (a staff member added later would miss earlier rows), and a hard-coded rule without a setting (a branch may want the old rule back).

**Addendum 2026-11-19 (contract 1.20.1):** on the owner's test server, phones that logged in before the server moved to 1.19.0 still showed only assigned customers: entries reach a device only when a customer changes, so nothing re-sent the rest of the branch. Fix: a generic *resync floor* in the change feed (`counters` `sync_floor:<reason>`). The customers module raises `customers-branch-wide` at its first boot on a database with history (a newly allocated seq), and `/sync/pull` answers `410 CURSOR_EXPIRED` for a cursor below it, so each such phone takes one fresh snapshot and keeps its outbox. Chosen over a data migration (the owner deploys by hand and may not run `db:migrate`) and over re-sending every customer (one snapshot per phone is cheaper than one feed entry per customer per branch). `GET /system/health` now reports `contract` so a deploy can be checked.
